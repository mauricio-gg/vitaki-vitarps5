# Architecture

What the code on `main` does today. Paths are relative to the repo root. Detail on the streaming pipeline and recovery is in [streaming.md](streaming.md); PSN internet play is in [psn.md](psn.md).

## Repo layout

| Path | What it is |
|---|---|
| `vita/src/`, `vita/include/` | The Vita client app (C). UI modules are in `vita/src/ui/` and `vita/include/ui/`. |
| `lib/` | The Chiaki core (session, control channel, Takion transport, video and audio receivers, discovery, registration, PSN hole punching in `lib/src/remote/`). It is a fork of upstream Chiaki with local changes, so treat it as upstream unless a change is needed. |
| `third-party/` | Bundled dependencies (curl, jerasure, gf-complete, libvita2d, nanopb, and others). |
| `tools/` | `tools/build.sh` is the only supported way to build: it runs the VitaSDK toolchain in Docker. |
| `assets/` | Images, SVGs and `psn-ca-bundle.pem`. |

Layering rule: `vita/` calls into `lib/`, never the other way round. Where `vita/` needs a `lib/` value it cannot include, it keeps a hand-copied constant (for example the priorities logged in `vita/src/host.c:512-513`).

## Vita client modules (`vita/src/`)

**Entry and main loop**
- `main.c`: `main()` (L143) runs `vita_init()` (power clocks, network and SSL/AVCDEC modules), creates the context, optionally starts discovery, then calls `draw_ui()`.
- `ui.c`: `draw_ui()`, the UI-thread main loop: input, screen dispatch, drawing, and deferred session finalization (`ui.c:520-521`).
- `context.c`, `vita/include/context.h`: the one global `context` (config, hosts, stream state) shared by all threads.

**Session lifecycle (`host*.c`)**
- `host.c`: `host_stream()` (L213) builds and starts a session; `host_default_video_profile()`.
- `host_callbacks.c`: the callbacks lib calls: `host_event_cb()` (connected, quit, rumble) and `host_video_cb()`.
- `host_quit.c`: `host_handle_quit_event()`, which classifies a quit and decides on teardown or recovery.
- `host_lifecycle.c`: `host_shutdown_media_pipeline()`, `host_finalize_session_resources()`, `host_finalize_deferred_session()`.
- `host_recovery.c`: soft-restart requests and post-reconnect degraded-mode handling.
- `host_input.c`: the input thread (controller, touch, motion sampling) and its priority constant.
- `host_feedback.c`: on-screen hints and the loss/overflow/resync reactions.
- `host_metrics.c`: per-stream counters and latency/FPS windows.
- `host_loss_profile.c`: latency-mode bitrate targets and loss-detection thresholds.
- `host_disconnect.c`: quit-reason labels, which reasons allow retry, the disconnect banner.
- `host_registration.c`: `host_register()` (PIN registration), the pairing attempt state and its UI API (`host_registration_poll()`, `host_registration_cancel()`, `host_registration_in_progress()`, `host_registration_take_result()`, declared in `host_registration.h`), and `host_wakeup()`.
- `host_registration_result.c`: pure. `HostRegistrationResult` (PAIRED, FAILED, UNREACHABLE, TIMEOUT, CANCELLED), the 30 s timeout constant, and `host_registration_resolve()`, which turns the lib event plus timeout, user cancel and stored-ok into the result. Tested natively in `test/pairing_result_tests.c`.
- `host_storage.c`: the host list: merging discovered and saved hosts, manual hosts, host copy helpers.

**Media**
- `video.c`: H.264 decode through `sceAvcdec`, with a queue feeding the VitaDecode thread, plus frame rendering.
- `audio.c`: `sceAudioOut` output, fed by `vita_audio_cb()`.
- `video_overlay.c`: in-stream overlays (indicators, exit hint, stats panel).

**Config and discovery**
- `config.c`, `config_values.c`, `config_hosts.c`, `config_migration.c`: the TOML settings file: parse, serialize, defaults, legacy migration, saved hosts. Two `[settings]` keys belong to the menus: `background_blur` (integer 0 to 3: None, Soft, Strong, Dark; default 0) and `show_button_hints` (bool, default true). A file without them loads with those defaults, and a `background_blur` outside 0 to 3 is reset to 0 with a warning in the log (`parse_background_blur()` in `config.c`).
- `room_icons.c`: room icons, the small picture each console wears on the Home list and the Connecting ring. There are six, in picker order: TV (default), Living room, Bedroom, Dorm, Office, Another place. A choice is stored per console MAC, not per registered record, so it survives re-registering and also works for consoles that are not paired or are only manual. It is saved as one `[[room_icons]]` block per console with a non-default icon (`mac` is 12 hex digits, `icon` is 1 to 5); choosing TV deletes the block. At most 32 consoles can carry a non-default icon; a 33rd choice is refused and logged. On load, an entry with a bad MAC, an all-zero MAC, an icon outside 1 to 5 or a repeated MAC is skipped with a warning. A console with no MAC (an all-zero `server_mac`) has no identity to store a choice under, so it always shows the TV and cannot be changed. The PNGs are `vita/assets/icons/room_<name>_<px>.png`, white on transparent, cut from the SVGs in `docs/design/ui-mocks/icons/` at 38 px (list rows), 48 px (the picker grid) and 64 px (the Connecting ring), so nothing is rescaled at run time. `ui_room_icons.c` loads all 18 textures once in `ui_room_icons_init()` and hands them out with `ui_room_icons_get()`; `ui_room_icon_for_host()` and `ui_room_icon_set_for_host()` (which saves the config) are what the screens call.
- `discovery.c`, `discovery_host.c`: `start_discovery()`/`stop_discovery()` around lib's discovery service, and merging results into the host list.
- `controller.c`, `controller_metadata.c`: controller mapping presets and storage.

**PSN**
- `psn_auth.c`: device login and OAuth tokens. `token_crypto.c`: AES-256-GCM encryption of persisted tokens. `psn_remote.c`: remote host list and per-connect preparation. `vita_dns.c`: DNS resolution for curl and sockets.

**Other**
- `logging.c`: asynchronous file logger (a queue drained by its own thread). `message_log.c`: in-app message log. `debug_tools.c`: debug-only tools, compiled when `VITARPS5_DEBUG_TOOLS` is set. `util.c`: small helpers.

## Menu frame setup

Each menu frame in `draw_ui()` (`ui.c`) calls `ui_background_prepare()` and then opens the main scene with `vita2d_start_drawing_advanced(NULL, 0)`, not `vita2d_start_drawing()`. The prepare pass does the `vita2d_pool_reset()` that `vita2d_start_drawing()` would do. At Background Blur Soft, Strong or Dark it also renders the wave into a small render target (240 x 136 for Soft, 60 x 34 shared by Strong and Dark), because vita2d can only draw into a render target in a scene of its own. The main scene then draws that target upscaled with bilinear filtering and a veil (`ui_background_draw()`). The main scene must not reset the pool again, or it would overwrite the vertices the target scene still needs. At None the prepare pass only resets the pool and the wave is drawn directly. The blur level is read from the config every frame, so a change applies at once. The targets are created on first use; if that fails, the log says so once and the background stays at None for the run (`ui_background.c`).

**Popups freeze the screen behind them** (`ui_freeze.c`, `ui_popup.c`). Opening a popup requests a capture. That frame is drawn as usual but without the screen's hint row and without the popup. After `vita2d_swap_buffers()`, `draw_ui()` calls `ui_freeze_frame_end()`, which waits for the GPU to finish the frame (`vita2d_wait_rendering_done()`), reads the finished frame from `vita2d_get_current_fb()` (after the swap that is the frame just drawn) and averages it 2 x 2 into one 480 x 272 texture (0.52 MB, created on the first capture and kept for the life of the app, no per-frame allocation). The copy is made from the finished display buffer, not by drawing the screen a second time, because the display is 4x MSAA and a render target is not: rendering the screen into a target would need an MSAA-none version of every textured and tinted program the screen uses. From the next frame, while a popup is open, `draw_ui()` skips the wave (`ui_background_prepare()` is replaced by the bare `vita2d_pool_reset()`, and `ui_background_draw()` by `ui_freeze_draw()`, one draw), and the screen draws only the popup layer, the scrim and the popup's hint row on top; the screen behind does not animate. Closing the popup releases the freeze at the end of that frame, so a screen that closes its popup mid-frame still draws that last frame over the copy. Leaving the screen releases it too. A screen reads `ui_freeze_is_capturing()` after its input has run, because input is what opens the popup; read at the top of the frame it is still false in the opening frame, and the popup's hint row would end up in the copy (Home did this until #303). The old full-screen Connect via popup (`ui_connect_popup_*`) is gone; Connect via is a C12 list popup. If the texture cannot be created the log says so at error level and the popup is drawn over the live screen and the scrim. Each capture logs `UI/POPUP_FREEZE` at debug level with the time spent waiting for the GPU and copying. The testing-only `UI/DRAWS` line names a frame drawn over the copy `popup`.

**Connection failures** (`ui_connect_failure.c`, `host_feedback.c`, `ui_home_options.c`). `host_set_hint()` runs on session and connection threads. When a hint is flagged as an error and `ui_console_hint_is_failure()` classes it as Error (the same rule that colours the console row; Retrying messages such as "Rebuilding stream at safer bitrate" are flagged as errors by their callers but never qualify), it calls `ui_connect_failure_post()`: under a lock it copies the console's display name (hostname when it has none) and the reason into one slot, with the host pointer kept only as an identity. A newer failure replaces an unread one. Clearing an error hint (empty message, `is_error`) calls `ui_connect_failure_clear()`, which drops the slot if it is that console's. The console's own `status_hint` is untouched, so the detail panel and row status work as before. Home calls `ui_connect_failure_take()` once per frame, after that frame's input and only while no popup is open and the screen stays on Home (a failure that arrives on another screen waits there). It opens the C14 popup over the frozen Home through `ui_home_options_open_failure()`: ERR tone, title "Could not connect", body "<name>: <reason>" with the raw reason (SPEC 3.3), buttons Close and Try again with focus on Try again. Try again runs `connect_console()`, so a Standby console is woken as on its row; Close, Cancel and a tap outside close. Try again is offered only while the console is in Home's list (`listed_console_index()` finds its host pointer in the console cache); otherwise the popup has Close only. The old global error popup (`ui_error_*`, `error_popup_active`, `error_popup_text`) is gone. The debug menu's "Remote Play error" entry now sets a real error hint on a console, so it goes down this path.

**PIN screen and pairing** (`ui_pin.c`). `draw_ui()` calls `ui_pin_on_enter()` when the screen changes to `UI_SCREEN_TYPE_REGISTER_HOST` (from Pair on an unpaired console, Confirm on one, or the Re-pair popup) and `ui_pin_frame()` every frame after. The screen is an XMB-chrome screen (`screen_has_xmb_chrome()`), so the old logo and wave sidebar are not drawn over it, and it has the `pin` name in the testing-only `UI/DRAWS` line. It always opens empty with focus on the first digit; on entry it drops a pairing result nobody collected (`host_registration_take_result()`), so an old result can never show for this console. Register calls `host_register(context.active_host, pin)`. While `host_registration_in_progress()` the screen calls `host_registration_poll()` every frame (that is what fires the 30 s timeout and reaps lib's thread) and then `host_registration_take_result()`; the field is locked (digits, Clear digit and Register at 45 percent, Cancel live) and the prompt reads "Pairing...". Cancel calls `host_registration_cancel()`; the CANCELLED result then returns to Home with no popup. Any other result opens the C14 popup over the frozen screen (copy from `ui_result_copy_pairing()`): PAIRED and OK go to Home with that console focused (`ui_home_focus_console()` marks the card cache stale, because a paired console sorts first), a failure's Close goes to Home, and Try again reopens the screen empty for the same console. If `host_register()` fails without reporting a result, the screen reports FAILED itself so it never waits for an attempt that is not running.

## Threads during a stream

Vita rule: a lower number is a higher priority. "Default" is the literal `0x10000100` that `chiaki_thread_create()` passes to `sceKernelCreateThread()` on Vita (`lib/src/thread.c:71-72`), so every lib thread starts there unless it lowers its own number.

| Thread | Created by | Priority / core |
|---|---|---|
| UI / main | the process; runs `main()` then `draw_ui()` | not set by the app; owns all vita2d drawing |
| VitaConnWorker | `ui_connection_start_thread()`, `vita/src/ui/ui_state.c:186-193`; runs `host_stream()` (L179) | `0x40` (64), 64 KiB stack |
| VitaLogThread | `vita_log_worker_init()`, `vita/src/logging.c:354` | `0x40` (64) |
| Session | `chiaki_session_start()`, `lib/src/session.c:322` | default |
| Ctrl | `chiaki_ctrl_start()` (called at `session.c:603`), `lib/src/ctrl.c:162` | default |
| Takion recv | `chiaki_takion_connect()`, `lib/src/takion.c:581`; one for the Senkusha probe (`senkusha.c:164`), one for the stream (`streamconnection.c:287`) | 64 (`TAKION_RECV_THREAD_PRIORITY`, `takion.c:64`, applied at `takion.c:1277`), core USER_0 |
| Takion send buffer | `chiaki_takion_send_buffer_init()`, `lib/src/takionsendbuffer.c:53`, called from the Takion thread (`takion.c:1345`) | default |
| GKCrypt key buffer | `chiaki_gkcrypt_init()`, `lib/src/gkcrypt.c:75`, only when a key buffer is configured | default |
| Congestion control | `chiaki_congestion_control_start()`, `lib/src/congestioncontrol.c:129`, called from `streamconnection.c:308` | default |
| Feedback sender | `chiaki_feedback_sender_init()`, `lib/src/feedbacksender.c:78` | 65 (`FEEDBACK_SENDER_THREAD_PRIORITY`, `feedbacksender.c:31`, applied at L413), no core pin |
| VitaDecode | `vita_h264_start()`, `vita/src/video.c:1447` | 64 (`VITA_DECODE_THREAD_PRIORITY`, `vita/include/video.h:39`, applied at `video.c:1330`), core USER_1 |
| Input | `host_stream()`, `vita/src/host.c:536`; body `host_input_thread_func()` | 96 (`VITA_INPUT_THREAD_PRIORITY`, `vita/include/host_input.h:11`, applied at `host_input.c:261`), affinity mask 0 |
| Discovery service | `chiaki_discovery_service_init()`, `lib/src/discoveryservice.c:75`, via `start_discovery()` | default; stopped while a stream runs (`host.c:456-460`) |

Notes:
- There is no audio thread. `vita_audio_cb()` (`vita/src/audio.c:204`) runs inline on whichever thread delivers the decoded audio. The call chain `takion_handle_packet_av()` (`takion.c:1828`) to `chiaki_audio_receiver_av_packet()` (`streamconnection.c:1280`) to the Opus decoder callback (`opusdecoder.c:95`) has no thread hand-off, so this is the Takion recv thread. On its first call the callback sets that calling thread to priority 64 (`VITA_AUDIO_THREAD_PRIORITY`, `vita/include/audio.h:5`) and core USER_2 (`audio.c:207-208`). The comments in `takion.c:1273-1276` and `video.c:1329` describe USER_2 as "audio" and USER_0 as "recv" as if they were separate threads; from the code they appear to be the same thread, re-pinned on the first audio frame. This is unverified on hardware.
- The log line `PIPE/PRIORITY` (`host.c:514`) prints decode, audio, recv, feedback and input priorities at each stream start.
- Registration (`regist.c:69`) and PSN hole punching (`lib/src/remote/holepunch.c:990`, `rudpsendbuffer.c:57`) start their own lib threads only on those paths; see [psn.md](psn.md).

## Session flow

1. **Launch.** `main()` initialises the system, builds `context` (`vita_chiaki_init_context()` parses the config, `context.c:27-28`), starts discovery if `config.auto_discovery` is set, and enters `draw_ui()`.
2. **Hosts appear.** Discovery results arrive through `discovery_cb()` (`discovery.c:277`) and are merged into `context.hosts` (`save_discovered_host()`, `discovery.c:116`). Saved and manual hosts come from config (`host_storage.c`). A console that is not yet registered is registered with `host_register()` (`host_registration.c:83`), which calls `chiaki_regist_start()`. Every attempt the UI starts ends in exactly one `HostRegistrationResult`, read once with `host_registration_take_result()` together with the console and a copy of its name. Pre-checks that fail before lib is called report at once (no hostname or discovery state is UNREACHABLE; a missing or undecodable PSN account id, or a failed start, is FAILED). `regist_cb` runs on lib's thread and only records the lib event under `attempt_mutex`; the UI thread calls `host_registration_poll()` once per frame, which stops the attempt 30 s after it started (`HOST_REGISTRATION_TIMEOUT_MS`; lib then reports CANCELED, mapped to TIMEOUT), and which calls `chiaki_regist_fini()` and reports the result once lib is done. `host_registration_cancel()` stops a running attempt and its CANCELED maps to CANCELLED (no popup). Stop and fini therefore only ever run on the UI thread. lib cannot tell a wrong PIN from an unreachable console, so both are FAILED. A successful registration counts only once it is stored: `store_registration()` returns true when the console is in `context.config.registered_hosts` and `config_serialize()` wrote the file, and sets `REGISTERED` on the host only then; a full table or a failed write is logged at error level with the console name and reported as FAILED, because the pairing would be lost at the next restart. A second `host_register()` while one runs is refused with an error log. Popup copy for the pairing results is in the pure `ui/ui_result_copy.c`. PSN remote hosts come from `psn_remote_refresh_hosts()` (called at `ui.c:496`).
3. **User picks a console.** The UI thread starts the connect through `start_connection_thread()` (`ui_state.c:321`, a wrapper for `ui_connection_start_thread()`), which creates the VitaConnWorker thread; that thread calls `host_stream(host)` (`ui_state.c:179`). The UI thread keeps drawing the connect overlay.
4. **`host_stream()`** (`host.c:213`), in execution order: chooses LAN or PSN (L218); builds the video profile with `host_default_video_profile()` (L310); on the PSN path runs the auth and session-creation stages (L323-357, `psn_remote_prepare_connect_host()` at L346); calls `chiaki_session_init()` (L429); stops discovery (L456-460); sets `session_init` under `finalization_mutex` (L463-466); wires the Opus audio sink (L482-486), the video callback `host_video_cb` (L488) and the event callback `host_event_cb` (L489); starts the decoder with `vita_h264_start()` (L498); calls `chiaki_session_start()` (L529); and finally creates the input thread (L536).
5. **Session thread** (`session_thread_func`, `lib/src/session.c:516`): starts the ctrl connection (`chiaki_ctrl_start`, L603), waits for it, runs Senkusha, which measures MTU and RTT (L702-708), then `chiaki_stream_connection_run()` (L761), which opens the Takion connection and starts congestion control and the feedback sender. This call blocks for the life of the stream.
6. **Events reach the Vita.** lib calls `host_event_cb()` (`host_callbacks.c:17`) on the session thread. `CHIAKI_EVENT_CONNECTED` resets the stream timers and flags. Video frames arrive on the Takion thread through `host_video_cb()`, which hands them to `vita_h264_decode_frame()` (`host_callbacks.c:146`), the producer side of the queue read by the VitaDecode thread; the UI thread draws the latest decoded frame with `vita_video_render_latest_frame()` (`ui.c:808`).
7. **Quit.** `CHIAKI_EVENT_QUIT` calls `host_handle_quit_event()` (`host_quit.c:42`) on the session thread. It snapshots state, decides whether to schedule recovery, then runs `host_shutdown_media_pipeline()` (`host_quit.c:125`), clears `session_init` and sets `session_finalize_pending` (L139-143).
8. **Teardown.** The session thread cannot join itself, so the UI thread does the join: `host_finalize_deferred_session()` (`ui.c:520-521`, `host_lifecycle.c`) joins the session thread and the input thread, then calls `chiaki_session_fini()`. If recovery was scheduled, the UI thread then starts the fallback connect (`ui.c:569-582`). Details are in [streaming.md](streaming.md).

### Media pipeline shutdown order

`host_shutdown_media_pipeline()` (`host_lifecycle.c:9`) is order-sensitive:
1. `is_streaming = false`, then `vita_h264_stop()` (joins VitaDecode) and a 2 ms delay, so the UI thread stops drawing the frame texture before it is freed;
2. `chiaki_opus_decoder_fini()`;
3. `vita_h264_cleanup()`;
4. `vita_audio_cleanup()`.
