# Architecture

What the code on `main` does today. Paths are relative to the repo root. Detail on the streaming pipeline and recovery is in [streaming.md](streaming.md); PSN internet play is in [psn.md](psn.md).

## Repo layout

| Path | What it is |
|---|---|
| `vita/src/`, `vita/include/` | The Vita client app (C). UI modules are in `vita/src/ui/` and `vita/include/ui/`. |
| `lib/` | The Chiaki core (session, control channel, Takion transport, video and audio receivers, discovery, registration, PSN hole punching in `lib/src/remote/`). It is a fork of upstream Chiaki with local changes, so treat it as upstream unless a change is needed. |
| `third-party/` | Bundled dependencies (curl, jerasure, gf-complete, libvita2d, nanopb, and others). |
| `tools/` | `tools/build.sh` is the only supported way to build: it runs the VitaSDK toolchain in Docker. Test and local builds carry version `0.1.N` (N bumped every build, `APP_VER` `00.06`). A release build passes `VITARPS5_RELEASE_VERSION` (e.g. `4.0.0`, set by the release workflow); that sets `version.h`, the versioned VPK name and `APP_VER` (major.minor only, a Vita format limit) and does not bump N. A beta release passes the plain `X.Y.Z`, builds with `--env beta` (`.env.beta`: like a stable build, with encrypted token storage and no debug tools, but verbose logging forced on regardless of the saved setting), and is tagged `vX.Y.Z-beta.N` (a GitHub pre-release; `tools/next_version.sh` picks the number). |
| `assets/` | Images, SVGs and `psn-ca-bundle.pem`. |

Layering rule: `vita/` calls into `lib/`, never the other way round. Where `vita/` needs a `lib/` value it cannot include, it keeps a hand-copied constant (for example the priorities logged in `vita/src/host.c:512-513`).

## Vita client modules (`vita/src/`)

**Entry and main loop**
- `main.c`: `main()` (L143) runs `vita_init()` (power clocks, network and SSL/AVCDEC modules), creates the context, optionally starts discovery, then calls `draw_ui()`.
- `ui.c`: `draw_ui()`, the UI-thread main loop: input, screen dispatch, drawing, and deferred session finalization (`ui.c:520-521`).
- `context.c`, `vita/include/context.h`: the one global `context` (config, hosts, stream state) shared by all threads.

**Session lifecycle (`host*.c`)**
- `host.c`: `host_stream()` (L213) builds and starts a session; `host_default_video_profile()`.
- `host_callbacks.c`: the callbacks lib calls: `host_event_cb()` (connected, quit, rumble) and `host_video_cb()`.
- `host_quit.c`: `host_handle_quit_event()`, which classifies a quit and decides on teardown or recovery.
- `host_lifecycle.c`: `host_shutdown_media_pipeline()`, `host_finalize_session_resources()`, `host_finalize_deferred_session()`.
- `host_recovery.c`: soft-restart requests and post-reconnect degraded-mode handling.
- `mic_decide.c` (`vita/include/mic_decide.h`, no SDK types; native test `test/mic_decide_tests.c`): `mic_decide()` is the one place that decides what the capture thread does on a pass, from `muted`, `stop_requested`, `sending` and `connected`: open the port and announce "mic on" (connecting the session first if needed), close the port and announce "mic off" (not on a stop, the session is going away), or nothing. While muted it never returns open, whatever else is true; only a change to unmuted can lead to an open. `mic_thread_func` reads `muted` once per pass, asks `mic_decide()` and carries out the answer, and drops a grain whose capture a mute landed in.
- `mic.c` (`vita/include/mic.h`), `mic_frame.c` (`vita/include/mic_frame.h`, no SDK types; native test `test/mic_frame_tests.c`): the microphone (#474), compiled into every build and linked with `SceAudioIn_stub`. `vitamic_on_stream_start()` (called from `host_stream()`) snapshots the `microphone` setting and decides whether the player's mute carries over; `vitamic_ui_tick()` (called every streaming frame from `draw_ui()`, `ui.c`) creates the capture thread once the stream is flowing; `vitamic_set_muted(muted, source)` and `vitamic_state()` are the interface for the UI. `vitamic_state()` is OFF (setting off, or not started yet), LIVE, MUTED or FAILED (the mic was meant to run this stream but its thread could not be created or started, or it ended by itself: `start_failed`, or the thread dead while `vitamic_stop()` has not asked it to exit; it lasts until the next stream's `vitamic_on_stream_start()`, and reads plain flags with no lock, so the input thread may call it); `vitamic_stop()` joins the thread and frees the encoder on every teardown path. The capture thread opens the VOICE port (16 kHz, 256-sample grains), `mic_frame.c` turns the grains into 480-sample stereo frames at 48 kHz, and the core's Opus encoder and audio sender send them. The path is in [streaming.md](streaming.md) section 6. Every log line starts with `MIC/`. The UI is `ui_mic.c` (below), `mic_touch.c` and `input_combos.c`.
- `host_input.c`: the input thread (controller, touch, motion sampling) and its priority constant. Motion (#455) is converted from the Vita frame to the DualSense frame by `motion_frame.c` (`vita/include/motion_frame.h`, no SDK types; native test `test/motion_frame_tests.c`): accel (x, y, z) becomes (-x, -z, y), because the Vita reports gravity and the DualSense the reaction to it, and gyro becomes (x, z, -y). Each new sample (only when `hostTimestamp` changed) goes through a `ChiakiOrientationTracker`, so the orientation sent is the tracker's, not the Vita's `deviceQuat`; the tracker's accel, gyro and orientation then pass the deadbands before they reach the controller state. Accel and orientation hold the last value inside their deadband; a gyro axis within its deadband of zero is sent as exactly 0, so a slowly settling axis cannot drift on the console. A sample with a non-finite value is dropped before the tracker. In testing builds it also swallows touches that begin on the Input test button, the resync widget or (panel open) the Close pill, each in a 48 px tall tap box under the button's own width, so nothing beside a button is swallowed (the panel body is not swallowed, so touches under it still reach the game), swallows L, R and Triangle while the panel combo is held, and publishes `debug_input_snapshot` every pass. In every build it runs `input_combos_step()` once per pass (the mute combo, and the panel combo in testing builds) and `mic_touch_judge()` on every front touch (see the two entries below). `input_test_click.c` (`vita/include/input_test_click.h`) measures the sent click (count and hold time) with no SDK types; native test in `test/input_test_tests.c`. A front touch keeps the zone it started in until the finger lifts (#460): `front_touch_zone.c` works out its outcome (button bits, L2/R2 held, touchpad touch or not) once, on the pass its Vita touch id first appears, and `host_input.c` applies that same outcome on every later pass wherever the finger is. A touchpad touch therefore follows the finger to the screen edges and across unmapped or button zones, a button touch never presses another button or becomes a touchpad touch, and a touch that started on nothing mapped presses nothing for its whole life. When the id stops being reported its outcome is dropped, so a new touch reusing the id is judged from its own start. The rear touch loop is separate and still reads the zone under the finger each pass. In testing builds the `INPUT_TEST/TOUCH` line's `zone=`, `out=`, `tp=` and `zones=` show this start-zone outcome; `slot=`, `cid=`, `sent=` and `raw=` show what was actually sent and the current raw position.
- `input_combos.c` (`vita/include/input_combos.h`, no SDK types; native test `test/input_combos_tests.c`): the hold-to-fire button combos the input thread watches (#474), each held `INPUT_COMBO_HOLD_MS` = 500 ms. **Mute: L + R + Select** toggles the microphone mute; it is watched only while `vitamic_state()` is LIVE or MUTED (otherwise L, R and Select go to the game as usual) and exists in every build. **Panel: L + R + Triangle** toggles the debug Input test panel and exists in testing builds only. Neither fires with Start down (L + R + Start is the stream-exit combo), a hold must be released before it can fire again, and while a combo is held its buttons are removed from what the game sees, from the first pass they are down. `host_input_thread_func` passes its `SCE_CTRL_*` bits in an `InputComboButtons`, and on a mute fire calls `ui_mic_request_toggle()`; on a panel fire it sets `input_test_toggle_request`.
- `mic_touch.c` (`vita/include/mic_touch.h`, no SDK types; native test `test/mic_touch_tests.c`): which front touches belong to the on-screen mic control (#474), in every build. `mic_touch_hit()` is the pure hit-test, shared by the touch filter and (through the same constants) the drawer: raw touch coordinates are halved to screen pixels; the bottom-centre button's area is 96 x 48 (x 432 to 527, y 488 to 535) at rest and, while its label shows, the pill (`MIC_BTN_LABEL_ON_W` 120 or `MIC_BTN_LABEL_MUTED_W` 144) plus 8 px on every side; the corner icon's area is its 32 px disc plus 8 px. `MicTouchTracker` judges a touch once, on the pass its Vita touch id first appears: one that starts inside the area is swallowed for its whole life and raises one tap (`mic_touch_judge()` reports it), one that starts outside stays the game's even if it slides in. `host_input.c` runs the filter on every front touch before the zone latch, so it takes precedence over any touchpad or button zone mapping (#460) and the touch never reaches the game.
- `front_touch_zone.c` (`vita/include/front_touch_zone.h`): the start-zone rule for front touches (#460), with no SDK types (native test in `test/front_touch_zone_tests.c`). It resolves a start position into an outcome (the any-touch mapping, the front grid zone, the left or right half, the corner arc and the centre zone, added together) and keeps a small table of outcomes keyed by Vita touch id. `host_input.c` calls `front_touch_zone_begin_pass()`, then `front_touch_zone_latch()` for each reported finger (resolves it on first sight, returns the kept outcome after that), then `front_touch_zone_end_pass()`, which forgets every id not reported that pass.
- `touchpad_gesture.c` (`vita/include/touchpad_gesture.h`): the timing rules for front touches mapped to the touchpad, with no SDK types (native test in `test/touchpad_gesture_tests.c`). `host_input.c` asks it once per input frame what to do. The feedback sender only compares controller states when it wakes, so a click has to be held `TOUCHPAD_CLICK_HOLD_MS` (50 ms) and has to happen while a finger is still on the pad. A single tap therefore keeps its touch active at its last position, holds the click for 50 ms, then releases click and touch together. A two-finger tap (second finger down within 150 ms of the first, neither moved) gives exactly one 50 ms click, pressed when the second finger lifts while both touches are still active; the first finger to lift is held for up to 200 ms and let go without a click if the partner moves or stays down. A two-finger hold (same two-finger start, neither moved, both still down `TOUCHPAD_TWO_FINGER_HOLD_MS` = 500 ms after the later finger started) presses the click and keeps it pressed while both fingers stay down; it ends on the first frame either finger is gone, never after that touch is released, and the finger still down is released on its lift without any click. A finger that moved before the threshold blocks the hold, moving afterwards does not end it, and a single finger never holds. A touch that moved is a drag: it stops at once and never clicks. A lift during a running click joins that click instead of starting another.
- `host_feedback.c`: on-screen hints and the loss/overflow/resync reactions.
- `host_metrics.c`: per-stream counters and latency/FPS windows.
- `host_loss_profile.c`: loss-detection thresholds per latency mode.
- `latency_policy.c`: the latency-mode start-bitrate ladder (1.5, 2.5, 3.5, 4.5, 6 and 10 Mbps for Ultra Low to Extreme), the PSN cap and the one-time Max migration (pure, no app state; native test in `test/latency_policy_tests.c`).
- `host_disconnect.c`: quit-reason labels, which reasons allow retry, the disconnect banner.
- `host_registration.c`: `host_register()` (PIN registration), the pairing attempt state and its UI API (`host_registration_poll()`, `host_registration_cancel()`, `host_registration_in_progress()`, `host_registration_take_result()`, declared in `host_registration.h`), and `host_wakeup()`.
- `host_registration_result.c`: pure. `HostRegistrationResult` (PAIRED, FAILED, UNREACHABLE, TIMEOUT, CANCELLED, NO_ACCOUNT_ID), the 30 s timeout constant, and `host_registration_resolve()`, which turns the lib event plus timeout, user cancel and stored-ok into the result. Tested natively in `test/pairing_result_tests.c`.
- `psn_account_id.c`: pure. The account ID rules: valid means 8 bytes and not all zero, the startup choice between registry and config.toml (a stored id counts only if it decodes to a valid one), which of the Vita's and the typed id is in use (`psn_account_id_in_use()`), parsing typed text (base64 or a decimal number, little-endian, stored as base64), and the log fingerprint (last 4 characters). Tested in `test/psn_account_id_tests.c`; `config_psn_account_id_in_use()` in `config.c` applies the in-use rule to the config. Design: `psn.md`, "Account ids".
- `host_storage.c`: the host list: merging discovered and saved hosts, manual hosts, host copy helpers. A manual host's `hostname` is written only by `save_manual_host()` and config load.

**Media**
- `video.c`: H.264 decode through `sceAvcdec`, with a queue feeding the VitaDecode thread, plus frame rendering.
- `audio.c`, `audio_queue.c`: `sceAudioOut` output on the VitaAudio thread, fed through a hand-off queue by `vita_audio_cb()` on the recv thread. `audio_queue.c` is the pure queue with the catch-up rule, tested natively in `test/audio_queue_tests.c`.
- `video_overlay.c`: in-stream overlays: the exit hint pill, the mute hint pill ("Mute mic: Hold L + R + Select", drawn with the Microphone setting on, stacked `UI_STREAM_HINT_STEP` = 40 px under the exit hint, or in its place when Show Exit Shortcut Hint is off, with the same 5 s hold and 0.5 s fade; the Select glyph is `hint_select.png`, `UI_BTN_SELECT`), the stats panel (which sits `UI_STREAM_HINT_STEP` lower while both hints are stacked, whether or not they have faded), the Network Unstable pill and the mic control (`ui_mic_draw()`) (C19 and C25, see `ui-mocks/SPEC.md` 3.5), counted as one `UI/DRAWS` frame named `overlay`; in testing builds it also calls `debug_tools_draw_widget()`, which draws the debug resync widget, the Input test button and, when open, the Input test panel.

**Config and discovery**
- `config.c`, `config_values.c`, `config_hosts.c`, `config_migration.c`: the TOML settings file: parse, serialize, defaults, legacy migration, saved hosts. A save is two halves. The caller formats the whole file in memory (`open_memstream`, so the serializers still write to a `FILE *`; the content is the same as before) and `config_writer.c` writes the bytes to the memory card on one low-priority thread. The write never opens the real file for writing: `config_writer_replace_file()` writes the whole buffer to `chiaki.toml.tmp` and checks the write and the close, then moves the old file to `chiaki.toml.bak`, renames the temp file to `chiaki.toml`, and deletes the backup (the Vita refuses to rename onto an existing file, so the old one has to move first; `sceIoRename` and `sceIoRemove` are called directly so the log carries the real error code). A whole copy of the config exists under one of the three names at every step, so a crash or power cut mid-save cannot leave an empty or half-written config. On any failure the old file is kept (or put back), the temp file is removed, the error is logged and the save returns false. `config_fix_legacy_queue_depth()` uses the same helper. On startup, before the config is read, `config_writer_recover_backup()` renames `chiaki.toml.bak` back to `chiaki.toml` if the real file is missing (the crash window between the first and second rename) and logs a warning; a leftover `.tmp` is ignored because it may be half written, and the next save overwrites it. A card write costs about 100 ms, which the UI thread used to wait for on every Settings press. `config_serialize_async()` returns once the buffer is queued and the writer logs a failed write; it is for UI-thread callers that only log (Settings, the pending-token save in `draw_ui()`, the PSN refresh commit). `config_serialize()` queues the same way and waits for its own write, returning true only when the file was written; it is for callers that act on the result (pairing in `host_registration.c`, manual-host edits in `host_storage.c`, the room icon choice, the PSN host refresh in `psn_remote.c`, the migration rewrite at boot). There is one pending slot and the latest save wins: a save queued while another still waits replaces it, so an older config is never written over a newer one. `main()` calls `config_writer_flush()` after `draw_ui()` returns. If the writer thread cannot be created, saves are written on the caller's thread and the failure is logged. Three `[settings]` keys hold the PSN account ids and the choice between them (`psn_account_id`, `psn_account_id_manual`, `psn_account_id_source`; see `psn.md`, "Account ids"). Five `[settings]` keys belong to the menus: `background` (integer 0 to 1: Waves, Glyphs; default 0), `background_blur` (integer 0 to 3: None, Soft, Strong, Dark; default 0; it is the Waves blur, so existing users keep their value), `background_blur_glyphs` (the same 0 to 3 for Glyphs; default 0), `theme` (integer 0 to 4: Ocean, Ember, Orchid, Moss, Graphite; default 0) and `show_button_hints` (bool, default true). A file without them loads with those defaults, and a `background` outside 0 to 1, a `background_blur` or `background_blur_glyphs` outside 0 to 3, or a `theme` outside 0 to 4 is reset to 0 with a warning in the log (`parse_background()`, `parse_blur_key()` and `parse_theme()` in `config.c`). `config_background_blur()` and `config_set_background_blur()` read and write the blur of the selected background; Settings, the Home detail summary and the renderer use them, so each background remembers its own level. One `[settings]` key belongs to the microphone (#474): `microphone` (bool, default false), read by `vitamic_on_stream_start()` each time a stream starts, so a change applies from the next stream, and `show_mic_button` (bool, default true: the bottom-centre button; false shows the corner icon instead; only used while `microphone` is on). Both have Settings rows under Controls.
- `room_icons.c`: room icons, the small picture each console wears on the Home list and the Connecting ring. There are six, in picker order: TV (default), Living room, Bedroom, Dorm, Office, Another place. A choice is stored per console MAC, not per registered record, so it survives re-registering and also works for consoles that are not paired or are only manual. It is saved as one `[[room_icons]]` block per console with a non-default icon (`mac` is 12 hex digits, `icon` is 1 to 5); choosing TV deletes the block. At most 32 consoles can carry a non-default icon; a 33rd choice is refused and logged. On load, an entry with a bad MAC, an all-zero MAC, an icon outside 1 to 5 or a repeated MAC is skipped with a warning. A console with no MAC (an all-zero `server_mac`) has no identity to store a choice under, so it always shows the TV and cannot be changed. The PNGs are `vita/assets/icons/room_<name>_<px>.png`, white on transparent, cut from the SVGs in `docs/design/ui-mocks/icons/` at 38 px (list rows), 48 px (the picker grid) and 64 px (the Connecting ring), so nothing is rescaled at run time. `ui_room_icons.c` loads all 18 textures once in `ui_room_icons_init()` and hands them out with `ui_room_icons_get()`; `ui_room_icon_for_host()` and `ui_room_icon_set_for_host()` (which saves the config) are what the screens call.
- `discovery.c`, `discovery_host.c`: `start_discovery()`/`stop_discovery()` around lib's discovery service, and merging results into the host list. Each discovered console gets its own record and never touches a manual host; the manual card is hidden while the console is discovered and returns when discovery loses it. `config_serialize_manual_hosts()` logs an error for any manual host it cannot save (zero MAC or empty address).
- `discovery_probe.c`: the unicast probe behind Pair new device > Enter IP address. It sends the discovery packet to the PS4 and PS5 ports of one address, resends every second, and gives up after `DISCOVERY_PROBE_DEADLINE_MS` (5 s); it works whether or not the broadcast discovery service runs. The UI thread advances it with `discovery_probe_poll()` once per frame. A reply becomes a standalone `VitaChiakiHost` that is never in `context.hosts`, so the discovery reaper cannot free it; if its MAC matches a paired console it carries that console's credentials and the `REGISTERED` flag (a re-pair). `discovery_probe_take_host()` hands it to the caller, who owns it: a successful registration moves it into `context.config.registered_hosts`; otherwise `discovery_probe_free_host()` releases it (and leaves a host the table holds alone). After a successful probe pairing `discovery_probe_save_manual_host()` saves the address as a manual host and calls `discovery_probe_sync_credentials()`, which copies the credentials to the broadcast-discovered entry of the same console, if there is one, so Home lists it at once (every saved manual host of the console gets them too). The PIN screen calls the same sync for a host that did not come from the probe. `discovery_probe_start()` refuses an address `ip_address_is_console_target()` rejects, and a reply whose host id is not 12 hex digits. `ip_address.c` is the one IPv4 parser (`ip_address_parse()`, `ip_address_format()`, plus the range check `ip_address_is_console_target()`), also used by the popup sort tie-break in `ui_console_status.c`; tested natively in `test/ip_address_tests.c`.
- `controller.c`, `controller_metadata.c`: controller mapping presets and storage.

**PSN**
- `psn_auth.c`: device login and OAuth tokens. `token_crypto.c`: AES-256-GCM encryption of persisted tokens. `psn_remote.c`: remote host list and per-connect preparation. `psn_auth_rules.c`: pure auth decision rules. `json_string.c`: pure JSON string-value helpers (key lookup, \uXXXX and surrogate decoding to UTF-8, len+1 buffer sizing) used by `psn_auth.c`, tested natively in `test/json_escape_tests.c`. `psn_background_refresh.c`: the token refresh and device-list fetch on a worker thread (startup, idle timer, Profile, after a login), committed by the UI thread (see psn.md). `vita_dns.c`: DNS resolution for curl and sockets.

**Other**
- `logging.c`: asynchronous file logger (a queue drained by its own thread). `message_log.c`: in-app message log. `debug_tools.c`: debug-only tools, compiled when `VITARPS5_DEBUG_TOOLS` is set: the resync widget and the Input test button (`debug_tools.h` holds their rectangles, the touch filter's classification and the snapshot struct). The Input test panel (#458, `debug_input_panel.c`) shows what the input thread SENT: front touch dots on a 1920x942 pad, the click light, count and hold time, and the sent accel/gyro next to the raw Vita sample, with two horizon boxes and a "sent differs from raw" warning. The sent motion is in the DualSense frame (see `host_input.c`), so a flat Vita reads level in both horizons and the same roll or pitch tilts both the same way. It opens with the button or by holding L + R + Triangle for 0.5 s (those three buttons are not sent to the game while held; it moved from L + R + Select when that became the mic mute combo, #474), and closes with the Close pill, the button or the same hold. It always starts closed on a new stream and is hidden with the other widgets during reconnect, resync and teardown. The numbers rebuild at 10 Hz; the dots, click light and horizons update every frame. `util.c`: small helpers.

**UI modules (`vita/src/ui/`)**: `ui_screens.c` (the Controller, Settings, PIN and Profile screens are no longer here), the connect logic of the Connecting screen in `ui_screen_draw_waking()`, and the Reconnecting screen's on/off check), `ui_components.c` (the debug menu only; every old widget and dialog is gone), `ui_home.c` (the XMB Home screen: category bar, item list, detail panel, top bar and hint row; the only screen on `UI_SCREEN_TYPE_MAIN`. The Consoles list starts with the `+ Pair new device` item, whose Confirm or tap opens the C29 popup at once; it has no Options and no long-press, and while the row directly above the focus is the item (it has faded out) the hint row adds D-pad up "Pair new device". Triangle on a console opens the Options column, which `ui_home_options.c` runs. A short Confirm press always just connects; Square only clears the filter. While a popup is open Home runs only the popup, and the frame is the frozen copy, the popup layer and the popup's hint row), `ui_home_options.c` (everything behind Triangle on a console: the C05 column, its rows from `ui_console_option_rows()`, what each row does, and the four popups it runs: Re-pair (C13), Connect via and Change icon (C12) from its rows, and "Could not connect" (C14) for a connection failure. Home passes it the focused console as a `UiHomeOptionsTarget` and a connect callback (`connect_console(host, force_psn)`, the one path Confirm, Connect via and Try again all use), and gets back the screen to show next. Re-pair, Connect via and Change icon keep the column open behind them; Cancel on any of them returns to it, and a route chosen in Connect via closes it and connects over Local Network or, forced, over PSN), `ui_category_bar.c` and `ui_xmb_list.c` (its interactive components), `ui_component.h` (the component model: rects, hit tests and the per-frame input snapshot, and the layer opacity: `ui_layer_set_alpha()` makes the text, shape, glow and logo helpers and the dimmed Home layers' own draws multiply an opacity into their colours, which is how the Options column dims Home to 25 percent and a popup fades in, as a tint on draws that happen anyway. Next to it is the global UI alpha, `ui_global_set_alpha()`, a second factor that only the main loop sets, to fade Home in over the splash; `ui_layer_color()` multiplies both, and `ui_layer_factor()` gives the product for draws that build their own vertex colours), `ui_theme.h` (colours, sizes and timings, the only place for such numbers in XMB code) and `ui_theme.c` (the five colour presets, Ocean, Ember, Orchid, Moss and Graphite, as one const table indexed by `context.config.theme`; `ui_theme_current()` returns the chosen entry, Ocean when the value is out of range, and the same pointer until the choice changes. The themed tokens in `ui_theme.h` read their RGB from it and keep their own alpha: the wave colours, ribbons, horizon and Glyphs backdrop, the panel, scrim, HUD, page wash, panel edge and glass veil tints, the accent, the halo and the mapped-cell line. Text, the OK, WARN and ERR colours, the white fills and lines and the QR colours never change with the theme. The Glyphs colours (`glyph_bg_a`, `glyph_bg_b`) are read by `ui_glyphs_build_gradient()` in `ui_background_glyphs.c` for the Glyphs gradient), `ui_detail_panel.c` (draws the info panel for the focused item) and `ui_home_detail.c` (what that panel says for each Home category; `ui_psn_auth_color()` colours the PSN Auth value and is shared with the Profile page), `ui_top_bar.c` (logo, cooldown banner, Wi-Fi as 0 to 3 signal bars read from the RSSI once a second (slashed icon when disconnected), battery, clock), `ui_hint_row.c` (button hints along the bottom, with tap detection; draws nothing when Show Button Hints is off, and has the Start glyph (the face symbols draw at 16 px) and the D-pad left-right, up-down and up glyphs; `ui_hint_row_glyph_width()` and `ui_hint_row_glyph_draw()` let other components draw the same glyph inside a label), `ui_pill.c` (C19, the 32 px pill: warn, unstable and plain variants; the plain one's label mixes text runs and button glyphs, measured once by `ui_pill_plain_layout()`; `ui_pill_draw()` takes a width the caller measured), `ui_stream_stats.c` (pure: the FPS value string of the stats panel), `ui_mic.c` (the on-screen microphone control of the stream overlay, #474; all of it runs on the UI thread except `ui_mic_request_toggle()` and the two touch-area getters. ## Start-up and splash

`init_ui()` (`ui.c`) brings the UI up behind the splash (`ui_splash.c`, SPEC 3.9, issues #366 and #398). In order:

1. `ui_asset_preload_start()` starts the preload worker (`ui_asset_preload.c`), a thread named `VitaUiPreload` at the UI thread's priority plus one (a higher number, clamped to 191), 128 KiB stack, not pinned to a core. It reads the logo, then both Roboto TTFs (whole files, no decode), then every PNG that start-up loads, in order of first use, decoding each into RGBA8 in RAM. It touches no vita2d object and logs nothing: the main thread logs failures when it meets them. If the thread cannot be created, that is logged and the list is decoded on the calling thread instead.
2. vita2d starts while the logo decodes. The clear colour is the scene colour. Loading runs with the vblank wait on (vita2d's default). The only place that switches it is the `draw_ui()` loop, through `ui_set_vblank_wait()` in `ui.c` (the only caller of `vita2d_set_vblank_wait()`, which remembers the state because vita2d has no getter). The main thread then waits for the logo, creates its texture, has `ui_splash_start()` sample the particles from the logo's RAM pixels (not from the texture, which is uncached memory), frees the pixels and logs `PIPE/SPLASH_INIT`. It then builds the background with `ui_background_init()` (the config is already loaded, so the saved theme and scene are known; it logs `PIPE/SPLASH_STEP name=background`), draws the first splash frame and sets the frame hook. The background is not a `STARTUP_STEPS` step any more.
3. The `STARTUP_STEPS` table runs on the main thread, in this order: `textures`, `cards`, `fonts`, `glow`, `shapes`, `room_icons`, `result_popup`, `home`, `connecting`, `toast`, `settings`, `profile`, `controller_page`, `pin`, `list_popup`, `pair_popup`, `input`, `psn_id`, `psn_refresh`. During start-up `ui_load_png_linear()` is served from the worker's pixels: it waits if the decode is not ready, creates the texture and fills it on the main thread, and frees the pixels. A path that is not in the hand-kept list in `ui_asset_preload.c` loads directly, with a `LOGW`. Fonts open with `vita2d_load_font_mem()` from the worker's bytes, which stay in memory for the whole run; if they are missing the font opens from the file, with a `LOGW`. Each splash frame during loading is the sharp background (`ui_background_draw_sharp()`: the saved scene and theme, never blurred, no render target, animated by time) and the logo, which fades in over the first `UI_SPLASH_LOGO_IN_MS` (0.45 s, ease-out cubic, from 97 percent to 100 percent size) and then holds. The frame hook draws a splash frame after each texture upload, while waiting on a decode, after each `ui_bake_white()` bake, and after each step. Every such frame goes through the same gate: a frame is drawn only when at least one display frame interval (16.667 ms) has passed since the last. The animation is time-based, so it never slows down.
4. `ui_asset_preload_finish()` joins the worker, clears the hook, and frees and warns about anything that was decoded but never used.
5. The glyph atlas is baked inside splash frames, because baking needs an open scene. Each frame bakes for at most `UI_PREWARM_FRAME_BUDGET_US` (8 ms) and resumes in the middle of a face on the next one. These frames are drawn whatever the frame gate says. The bake is 588 glyphs (Regular 297, Light 291; 97 per face plus the probe glyphs), and `init_ui()` loops over these frames until it is done, so Home does not start until the bake ends (the dissolve does not start before `UI_SPLASH_MIN_HOLD_MS`, 1.0 s, from the splash start, so a bake that ends inside that window adds no wait).
6. Loading is done (`ui_splash_loading_done()`); the vblank wait has been on all along. D = max(loading done, 1.0 s) is fixed as the moment the dissolve starts. Splash frames (background and logo) continue until D.
7. `draw_ui()` takes over at D. From D the splash is on the reversed clock of #366: the same particles, seed and motion played backwards, so they lift off the logo and fly to the screen edges, and the crisp logo thins out (alpha exponent `UI_SPLASH_LOGO_GAMMA_OUT`, 3.0). The dissolve lasts `UI_SPLASH_DISSOLVE_MS` (1.02 s), so the splash ends at D + 1.02 s (`ui_splash_draw_exit()`, the last draw of the frame). The timeline maths is `ui_splash_timeline.c`. Home is not drawn before D + 0.40 s. From then `ui_splash_home_opacity()` rises as an ease-out cubic to 1 at D + 0.70 s. `draw_ui()` reads it once per frame and uses it three ways. It sets the global UI alpha (`ui_global_set_alpha()`) around the screen's draws, so Home fades in as one, including its vignette. It passes it to `ui_background_draw_crossfade()`, which draws the sharp scene and then the user's blur level over it at that alpha (the blurred target, and `UI_GLASS_VEIL`, `UI_GLASS_FROST` or `UI_GLASS_VEIL_DARK` at their own alpha times it; blur None draws nothing extra). At 1 (D + 0.70 s to D + 1.02 s) the background is drawn by `ui_background_draw()` as in Home, so the end of the splash shows no jump. And it picks the frames that prepare the blur chain: from D `ui_background_prepare()` runs as on any menu frame, which creates the blur targets on that first frame and renders the chain, while before D only the pool is reset and no target is created or rendered. If the targets cannot be created, the crossfade is skipped, the background stays sharp and one `LOGE` with the blur level is logged. Home takes no input before D + 0.70 s (`ui_splash_home_input_enabled()`): `block_inputs_for_transition()` runs on every frame until then, so a button or finger still held at that moment stays blocked until released. Home is entered on its first visible frame.

A new button press or touch, once loading is done and before D, moves D to now, but never before the logo has finished fading in. At any other time it does nothing: it never skips loading, and it does nothing once the dissolve runs. Buttons and fingers already down at launch do not count.

The `psn_refresh` step only starts the startup PSN refresh in a background thread (`psn_background_refresh.c`) and returns, so the splash does not wait for the network; `draw_ui()` commits the result once the thread is done. How the hand-off, the commit and the failure cases work is in [psn.md](psn.md), "Tokens: storage and refresh".

The particles are one triangle list written into vita2d's per-frame pool, so nothing is allocated per frame. The particle array is allocated once at splash start and freed when the dissolve ends. The draws per frame, back to front: before D the sharp background (12 draws for Waves, 2 for Glyphs) and the logo (1). From D the background (the blur levels add the target and the veils during the crossfade), Home at the global alpha once it shows, the logo (1) and the particles (1). Home's top bar, list, panel, hint row, text and textures reach the global alpha through `ui_layer_color()`; the vignette scales its own vertex colours by `ui_layer_factor()`.

Testing builds log these lines (`LOGD`). Times are absolute process time in microseconds, except the durations:
- `PIPE/SPLASH_INIT vita2d_us= logo_wait_us= logo_upload_us= sample_us=`: durations of vita2d init, the wait for the logo decode, the logo texture upload and the particle sampling.
- `PIPE/ASSET path= read_us= decode_us= upload_us= w= h=`: one line per preloaded PNG, with the worker's read and decode times and the main thread's upload time. `PIPE/ASSET font path= read_us= bytes=`: the same for each TTF.
- `PIPE/SPLASH_FIRST_FRAME us=`: the first splash frame was presented.
- `PIPE/SPLASH_DISSOLVE loaded_ms= dissolve_start_ms= ui_full_ms= end_ms=`: logged when the splash ends. All four are milliseconds from the splash start: loading done (L), the dissolve start (D), Home fully opaque and taking input (D + 0.70 s), and the splash end (D + 1.02 s).
- `PIPE/SPLASH_STEP name= us=`: one line per step with its duration. A baked glyph face logs `PIPE/SPLASH_STEP name=glyphs_<n> us= frames= metrics_us= first_glyph_us=` when it completes: its total time, the splash frames it took, and the times spent measuring metrics and until the first glyph.
- `PIPE/UI_PREWARM_DONE us=`: the last glyph face is baked.
- `PIPE/PSN_REFRESH begin origin= us=` and `done origin= us= worker_us= commit_us= token= hosts=`: a background refresh started, and was committed. `origin` is `startup`, `idle`, `profile` or `login` (see psn.md).
- `PIPE/CONFIG_SAVE bytes= format_us= write_us= coalesced= ok=`: one line per config write, logged by the writer thread. `format_us` is the time the caller spent formatting the file, `write_us` the temp write and renames on the card, `coalesced` how many queued saves this write replaced, `ok` 1 or 0.
- `PIPE/SPLASH_DONE frames= expected= elapsed_us= load_done_us= max_gap_us= max_gap_step=`: the dissolve has finished. `load_done_us` is the absolute process time at which loading finished. `frames` is the number of splash frames drawn and `expected` is the count a steady frame rate would give (elapsed time divided by the frame interval). `elapsed_us` is the splash's total time, and `max_gap_us` is the longest gap between two presented splash frames, both durations. `max_gap_step` is the longest step inside that gap.
- `PIPE/UI_FIRST_HOME_FRAME us=`: the first Home frame was presented.

**Tear probe `UI/SWAPS`** (testing builds, ticket #442; `ui_draw_stats.c`, `UI_DRAW_STATS_SWAP()`). Called right after each of the three `vita2d_swap_buffers()` sites: the main loop in `draw_ui()` (named like its `UI/DRAWS` frame, so `popup` over a frozen screen), `splash_frame()` (`splash`) and the stream present in `vita_video_render_latest_frame()` (`stream`). A screen the draw counter does not name logs as `other`. One line per screen and per second, or earlier when the screen name changes (the partial window is logged under the old name first, so every swap belongs to exactly one line).
`UI/SWAPS screen= swaps= nowait= same_vcount= vcount_delta_max=`
- `swaps`: buffer swaps in the window.
- `nowait`: swaps made while the vblank wait was off (the state `ui_set_vblank_wait()` last set, so it is true to what vita2d was told). The wait is off only while the stream picture is shown, so a correct run has `nowait` above 0 only on `screen=stream`.
- `same_vcount`: swaps where `sceDisplayGetVcount()` had not advanced since the previous swap, so two swaps were submitted within one refresh. With the wait off this can tear. The first swap after a screen change is compared with the previous swap, whatever its screen, and counts for the new screen.
- `vcount_delta_max`: the largest vcount advance between two consecutive swaps; 1 is every refresh, 2 or more is a dropped refresh. The step of the first swap after a screen change is left out, because a gap between screens (stream to menu) is not a dropped refresh.
The vcount is read on the app thread right after `vita2d_swap_buffers()` returns, not at the actual flip: vita2d queues the flip to its display callback. So `same_vcount` means two swaps were submitted within one refresh, not that the panel showed a tear. Example (made-up numbers): `UI/SWAPS screen=home swaps=60 nowait=0 same_vcount=0 vcount_delta_max=1`.

## Menu frame setup

Each menu frame in `draw_ui()` (`ui.c`) calls `ui_background_prepare()` and then opens the main scene with `vita2d_start_drawing_advanced(NULL, 0)`, not `vita2d_start_drawing()`. The prepare pass does the `vita2d_pool_reset()` that `vita2d_start_drawing()` would do. At Background Blur Soft, Strong or Dark it also renders the selected scene (Waves or Glyphs) into a 480 x 272 render target (half the screen) and averages it down by exact 2:1 passes: 240 x 136 for Soft, then 120 x 68, then 60 x 34 shared by Strong and Dark. The scene is drawn big and averaged because a render target without MSAA takes one sample per texel, and drawing straight into a small target would point-sample it and turn into blocks. vita2d can only draw into a render target in a scene of its own, which is why the prepare pass exists. The main scene then draws the Soft or the Strong and Dark target upscaled with bilinear filtering and a veil (`ui_background_draw()`). Glyphs draws its symbols into the 480 x 272 target with feathered edges (a two-quad tent per outline segment, alpha fading to 0 one texel either side), because the 2.5 px stroke is thinner than a texel there and a hard stroke would land on one or two texels depending on where it sits (#400); the screen and the splash's sharp half still draw the hard stroke, and Waves is drawn the same in both. The main scene must not reset the pool again, or it would overwrite the vertices the target scene still needs. At None the prepare pass only resets the pool and the scene is drawn directly. The blur level is read from the config every frame, so a change applies at once. The targets are created on first use; if that fails, the log says so once and the background stays at None for the run (`ui_background.c`).

**Popups freeze the screen behind them** (`ui_freeze.c`, `ui_popup.c`). Opening a popup requests a capture. That frame is drawn as usual but without the screen's hint row and without the popup. After `vita2d_swap_buffers()`, `draw_ui()` calls `ui_freeze_frame_end()`, which waits for the GPU to finish the frame (`vita2d_wait_rendering_done()`), reads the finished frame from `vita2d_get_current_fb()` (after the swap that is the frame just drawn) and averages it 2 x 2 into one 480 x 272 texture (0.52 MB, created on the first capture and kept for the life of the app, no per-frame allocation). The copy is made from the finished display buffer, not by drawing the screen a second time, because the display is 4x MSAA and a render target is not: rendering the screen into a target would need an MSAA-none version of every textured and tinted program the screen uses. From the next frame, while a popup is open, `draw_ui()` skips the wave (`ui_background_prepare()` is replaced by the bare `vita2d_pool_reset()`, and `ui_background_draw()` by `ui_freeze_draw()`, one draw), and the screen draws only the popup layer, the scrim and the popup's hint row on top; the screen behind does not animate. Closing the popup releases the freeze at the end of that frame, so a screen that closes its popup mid-frame still draws that last frame over the copy. Leaving the screen releases it too. A screen reads `ui_freeze_is_capturing()` after its input has run, because input is what opens the popup; read at the top of the frame it is still false in the opening frame, and the popup's hint row would end up in the copy (Home did this until #303). The old full-screen Connect via popup (`ui_connect_popup_*`) is gone; Connect via is a C12 list popup. If the texture cannot be created the log says so at error level and the popup is drawn over the live screen and the scrim. Each capture logs `UI/POPUP_FREEZE` at debug level with the time spent waiting for the GPU and copying. The testing-only `UI/DRAWS` line names a frame drawn over the copy `popup`.

**Connection failures** (`ui_connect_failure.c`, `host_feedback.c`, `ui_home_options.c`). `host_set_hint()` runs on session and connection threads. When a hint is flagged as an error and `ui_console_hint_is_failure()` classes it as Error (the same rule that colours the console row; Retrying messages such as "Rebuilding stream at safer bitrate" are flagged as errors by their callers but never qualify), it calls `ui_connect_failure_post()`: under a lock it copies the console's display name (hostname when it has none) and the reason into one slot, with the host pointer kept only as an identity. A newer failure replaces an unread one. Clearing an error hint (empty message, `is_error`) calls `ui_connect_failure_clear()`, which drops the slot if it is that console's. The console's own `status_hint` is untouched, so the detail panel and row status work as before. Home calls `ui_connect_failure_take()` once per frame, after that frame's input and only while no popup is open and the screen stays on Home (a failure that arrives on another screen waits there). It opens the C14 popup over the frozen Home through `ui_home_options_open_failure()`: ERR tone, title "Could not connect", body "<name>: <reason>" with the raw reason (SPEC 3.3), buttons Close and Try again with focus on Try again. Try again runs `connect_console()`, so a Standby console is woken as on its row; Close, Cancel and a tap outside close. Try again is offered only while the console is in Home's list (`listed_console_index()` finds its host pointer in the console cache); otherwise the popup has Close only. The old global error popup (`ui_error_*`, `error_popup_active`, `error_popup_text`) is gone. The debug menu's "Remote Play error" entry now sets a real error hint on a console, so it goes down this path.

**PIN screen and pairing** (`ui_pin.c`). `draw_ui()` calls `ui_pin_on_enter()` when the screen changes to `UI_SCREEN_TYPE_REGISTER_HOST` (from a console chosen in the Pair new device popup, or the Re-pair popup) and `ui_pin_frame()` every frame after. It has the `pin` name in the testing-only `UI/DRAWS` line. It always opens empty with focus on the first digit; on entry it drops a pairing result nobody collected (`host_registration_take_result()`), so an old result can never show for this console. Register calls `host_register(context.active_host, pin)`. While `host_registration_in_progress()` the screen calls `host_registration_poll()` every frame (that is what fires the 30 s timeout and reaps lib's thread) and then `host_registration_take_result()`; the field is locked (digits, Clear digit and Register at 45 percent, Cancel live) and the prompt reads "Pairing...". Cancel calls `host_registration_cancel()`; the CANCELLED result then returns to Home with no popup, and so do Cancel before pairing and a failure's Close, all with the Pair new device item focused (`ui_home_focus_pair_item()`; a re-pair focuses the console). Any other result opens the C14 popup over the frozen screen (copy from `ui_result_copy_pairing()`): PAIRED and OK go to Home with that console focused (`ui_home_focus_console()` marks the card cache stale, because a paired console sorts first), a failure's Close goes to Home on the Pair new device item (the console, for a re-pair), and Try again reopens the screen empty for the same console. A Triangle re-pair keeps the old pairing until a new one succeeds: `ui_screens_repair_host()` only makes the console the active host, so its credentials, `REGISTERED` flag, registered-table slot and config file stay as they were. `ui_pin_on_enter()` decides once whether the screen is a re-pair (the active host is already `REGISTERED` and did not come from the probe); for a re-pair, Cancel before pairing, a cancelled attempt and a failure's Close focus that console on Home instead of the item. Success overwrites the credentials in place in the host's existing `registered_state` (written on lib's registration thread, in place, into the host's existing allocation; the pointer is never freed or swapped, so a concurrent reader can never touch freed memory) and repoints the registered-table slot of that MAC at the host; the PIN screen then calls `discovery_probe_sync_credentials()` so the console's other live entries get the new credentials too, with the same partial-save warning as below. If the console accepts the PIN of a re-pair but `config_serialize()` fails, `store_registration()` has already overwritten the credentials in memory, so the result is FAILED ("Pairing failed", and the log line "Failed to write the config; the registration of ... would be lost at restart.") while the new credentials are used until the app restarts and the old ones come back from the config file after it; pairing again fixes it. A re-pair cannot hit the max-registered-hosts failure, because the console is already in the table. A host from the IP probe (`ui_pin_adopt_probed_host()`) is owned by this screen: PAIRED hands it to the registered table and saves the address as a manual host (`discovery_probe_save_manual_host()`, which also gives the new credentials to the discovered entry and to every saved manual host of that console; an entry used by a running session is skipped; the registered-table entry a re-pair replaces is left alone, never freed). This runs when the result arrives, before the popup opens: if the address or any credentials could not be saved the popup is the warning "Console paired" (`ui_result_copy_paired_partial()`, one OK button) instead of the plain one. OK focuses the console Home lists for it, or the Pair new device item when it lists none; Cancel on the field, a cancelled attempt and a failure's Close release it with `discovery_probe_free_host()`, only once no attempt is running; Try again keeps it. If `host_register()` fails without reporting a result, the screen reports FAILED itself so it never waits for an attempt that is not running.

## Session flow

1. **Launch.** `main()` initialises the system, builds `context` (`vita_chiaki_init_context()` parses the config, `context.c:27-28`), starts discovery if `config.auto_discovery` is set, and enters `draw_ui()`.
2. **Hosts appear.** Discovery results arrive through `discovery_cb()` (`discovery.c:268`) and are merged into `context.hosts` (`save_discovered_host()`, `discovery.c:116`). Saved and manual hosts come from config (`host_storage.c`). A manual host's record is the same struct in `context.config.manual_hosts` (what is saved) and `context.hosts` (what is listed), so discovery never reuses or writes it: a discovered console always gets its own record in an empty slot, and `update_context_hosts()` hides the manual card while a discovered record with the same MAC exists and puts it back when that record is removed (#234). A console that is not yet registered is registered with `host_register()` (`host_registration.c:83`), which calls `chiaki_regist_start()`. Every attempt the UI starts ends in exactly one `HostRegistrationResult`, read once with `host_registration_take_result()` together with the console and a copy of its name. Pre-checks that fail before lib is called report at once (no hostname or discovery state is UNREACHABLE; a missing, undecodable, wrong-length or all-zero PSN account id is NO_ACCOUNT_ID, shown as "Sign in to PSN on this Vita..." copy; a failed start is FAILED). A valid id is 8 bytes and not all zero (`psn_account_id_is_valid()`, pure, `psn_account_id.c`); when an attempt starts it logs the last 4 base64 characters of the id. `regist_cb` runs on lib's thread and only records the lib event under `attempt_mutex`; the UI thread calls `host_registration_poll()` once per frame, which stops the attempt 30 s after it started (`HOST_REGISTRATION_TIMEOUT_MS`; lib then reports CANCELED, mapped to TIMEOUT), and which calls `chiaki_regist_fini()` and reports the result once lib is done. `host_registration_cancel()` stops a running attempt and its CANCELED maps to CANCELLED (no popup). Stop and fini therefore only ever run on the UI thread. lib cannot tell a wrong PIN from an unreachable console, so both are FAILED. A successful registration counts only once it is stored: `store_registration()` returns true when the console is in `context.config.registered_hosts` and `config_serialize()` wrote the file, and sets `REGISTERED` on the host only then; a full table or a failed write is logged at error level with the console name and reported as FAILED, because the pairing would be lost at the next restart. A second `host_register()` while one runs is refused with an error log. Popup copy for the pairing results is in the pure `ui/ui_result_copy.c`. PSN remote hosts come from `psn_remote_refresh_hosts()` (called at `ui.c:506`).
3. **User picks a console.** The UI thread starts the connect through `start_connection_thread()` (`ui_state.c:321`, a wrapper for `ui_connection_start_thread()`), which creates the VitaConnWorker thread; that thread calls `host_stream(host)` (`ui_state.c:179`). The UI thread keeps drawing the connect overlay.
4. **`host_stream()`** (`host.c:213`), in execution order: chooses LAN or PSN (L218); builds the video profile with `host_default_video_profile()` (L310); on the PSN path runs the auth and session-creation stages (L323-357, `psn_remote_prepare_connect_host()` at L346); calls `chiaki_session_init()` (L429); stops discovery (L456-460); sets `session_init` under `finalization_mutex` (L463-466); wires the Opus audio sink (L482-486), the video callback `host_video_cb` (L488) and the event callback `host_event_cb` (L489); starts the decoder with `vita_h264_start()` (L498); calls `chiaki_session_start()` (L529); and finally creates the input thread (L536).
5. **Session thread** (`session_thread_func`, `lib/src/session.c:516`): starts the ctrl connection (`chiaki_ctrl_start`, L603), waits for it, runs Senkusha, which measures MTU and RTT (L702-708), then `chiaki_stream_connection_run()` (L761), which opens the Takion connection and starts congestion control and the feedback sender. This call blocks for the life of the stream.
6. **Events reach the Vita.** lib calls `host_event_cb()` (`host_callbacks.c:17`) on the session thread. `CHIAKI_EVENT_CONNECTED` resets the stream timers and flags. Video frames arrive on the Takion thread through `host_video_cb()`, which hands them to `vita_h264_decode_frame()` (`host_callbacks.c:146`), the producer side of the queue read by the VitaDecode thread; the UI thread draws the latest decoded frame with `vita_video_render_latest_frame()` (`ui.c:808`).
7. **Quit.** `CHIAKI_EVENT_QUIT` calls `host_handle_quit_event()` (`host_quit.c:42`) on the session thread. It snapshots state, decides whether to schedule recovery, then runs `host_shutdown_media_pipeline()` (`host_quit.c:125`), clears `session_init` and sets `session_finalize_pending` (L139-143).
8. **Teardown.** The session thread cannot join itself, so the UI thread does the join: `host_finalize_deferred_session()` (`ui.c:520-521`, `host_lifecycle.c`) joins the session thread and the input thread, then calls `chiaki_session_fini()`. If recovery was scheduled, the UI thread then starts the fallback connect (`ui.c:569-582`). Details are in [streaming.md](streaming.md).

### Media pipeline shutdown order

`host_shutdown_media_pipeline()` (`host_lifecycle.c:9`) is order-sensitive:
0. `vitamic_stop()` (#474), before anything else, even when the media pipeline was never initialised: the mic thread sends through the session, so it is joined and its encoder freed while the session still exists. `host_finalize_session_resources()` and `host_finalize_deferred_session()` call it again just before `chiaki_session_fini()` as a no-op safety net.
1. `is_streaming = false`, then `vita_h264_stop()` (joins VitaDecode) and a 2 ms delay, so the UI thread stops drawing the frame texture before it is freed;
2. `chiaki_opus_decoder_fini()`;
3. `vita_h264_cleanup()`;
4. `vita_audio_cleanup()` (signals the VitaAudio thread, joins it, then frees the queue and buffers; the Takion thread is already joined by then, see [streaming.md](streaming.md) section 7).
