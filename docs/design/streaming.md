# Streaming pipeline and recovery

What the code on `main` does today between "a UDP packet arrives from the console" and "a picture is on the screen", and what happens when the stream dies. For the list of threads and who owns them, see [architecture.md](architecture.md). Citations are `path:line` against the tree at the time of writing; line numbers drift, function names are the stable handle.

## 1. Pipeline at a glance

```
 PS5 --UDP--> [Takion recv thread, USER_0, prio 64]
                 | control packets -> reorder queue (256) -> stream connection
                 | video packets -> chiaki_video_receiver_av_packet()
                 |       frame assembly + FEC + reference checks
                 |       host_video_cb() -> vita_h264_decode_frame()  (producer)
                 v
        decode_queue[4]  (SPSC ring, decode_q_mtx / decode_q_cond)
                 |
                 v
        [VitaDecode thread, USER_1, prio 64]  sceAvcdecDecode -> frame_texture
                 |  frame_ready_for_display = true
                 v
        [UI thread]  vita_video_render_latest_frame() -> vita2d draw + swap

 audio packets -> Opus decode inline on the recv thread -> vita_audio_cb copies the frame into a
                 hand-off queue (short mutex hold) and returns
                       |
                       v
        [VitaAudio thread, USER_2, prio 64]  pops one device buffer -> sceAudioOutOutput (blocks)
 loss stats    -> [congestion control thread, every 200 ms] -> PS5
 input         -> [feedback sender thread, prio 65] -> PS5
```

The recv thread never waits on the decoder for a whole frame: it copies the compressed frame into a queue slot and returns (section 5). It does not wait on the sound hardware either: it copies the decoded audio frame into a queue and returns (section 6).

## 2. Receive (Takion)

- **Thread.** `takion_thread_func` is created in `chiaki_takion_connect` (`lib/src/takion.c:617`, `chiaki_thread_create`). On Vita it sets itself to priority `TAKION_RECV_THREAD_PRIORITY` = 64 and pins to CPU `USER_0` (`takion.c:65` define, `takion.c:1602-1603` apply). Decode runs on `USER_1` and sound output on `USER_2`. Nothing re-pins the recv thread: it stays on `USER_0` at 64 for the whole stream (#416; the audio callback runs on this thread but only queues the frame, section 6).
- **Socket buffer.** On Vita the advertised window `TAKION_A_RWND` is `0x80000` (512 KB, `takion.c:51`), copied into `takion->a_rwnd` (`takion.c:330`) and applied with `setsockopt(SO_RCVBUF)` in both connect paths (`takion.c:370`, `takion.c:491`). The kernel's actual value is read back and logged as `Takion SO_RCVBUF requested=... actual=...` (`takion.c:380-381`, `501-502`). The same value is used for `SO_SNDBUF` (`takion.c:386`, `507`).
- **Drain loop.** After the blocking `takion_recv` wakes the thread, it pulls up to `TAKION_RECV_DRAIN_MAX` = 256 more packets with zero-timeout reads before blocking again (`takion.c:80`, loop at `takion.c:1432-1441`). The code intends the zero-timeout read to be a poll that returns at once when the socket is empty. On hardware it is not known to behave like that: the first `PIPE/RECVBUF` log hit the cap in 108 of 135 windows at stream rates far too low to have a standing backlog, so the loop may be spending its time inside the reads (section 9.3, "What the first hardware log showed").
- **Packet dispatch.** `takion_handle_packet` (`takion.c:1810`) sends control packets to the message path and video/audio packets straight to `takion_handle_packet_av` (`takion.c:1820-1828`). If encryption is on and the remote key is not ready yet, AV packets are parked in a postpone list instead (`takion.c:1825-1826`).
- **The reorder queue is control-channel only.** `takion->data_queue` (256 entries, `TAKION_REORDER_QUEUE_SIZE_EXP` 8, `takion.c:69`, init at `takion.c:1285`) is fed from the message path. The comment at `takion.c:1071` states video and audio never enter it, so its overflow/drop log lines say nothing about video loss.
- **Transient errors (ENOBUFS) are not fatal.** In `takion_recv` (`takion.c:1616` onward) a transient error from `select()` or `recv()` is counted, logged at most once a second (`TAKION_RECV_TRANSIENT_LOG_INTERVAL_MS` = 1000), and retried after a backoff of `TAKION_RECV_TRANSIENT_RETRY_DELAY_MS` = 5 ms (`takion.c:140-143`). The non-blocking drain call (timeout 0) only counts and returns, it never sleeps (`takion.c:1641`, `1688`). The call gives up with `CHIAKI_ERR_NETWORK` only after more than `TAKION_RECV_TRANSIENT_MAX_CONSECUTIVE` = 400 consecutive hits AND at least `TAKION_RECV_TRANSIENT_MIN_PERSIST_MS` = 1500 ms since the first (`takion.c:1644-1646`, `1691-1693`). Any successful receive resets the count.
- **Why the backoff has a fallback.** `takion_recv_transient_backoff` (`takion.c:1606`) first waits on the stop pipe. On Vita the stop pipe is itself a socket, so during an ENOBUFS storm that wait fails instantly; when it does not report a timeout or a cancel, the function falls back to `chiaki_sleep_ms`. Without that, the retry budget was burned in a tight spin (explained in the comment at `takion.c:113-139`). Giving up is what ends the session as a transport failure (section 8).
- **The "jitter" number is not network jitter.** `takion->jitter_stats.jitter_us` is an EWMA (weight 1/8) of how much the gap between consecutive control-channel packets changes (`takion.c:2171-2176`). Video and audio never touch it. Video has its own, separate figure (`video_jitter_stats`, `takion.c:2454`). The log line starting `Latency metrics` prints `senkusha_rtt` (a single round trip measured during the handshake, never updated afterwards, `host_metrics.c:1025-1031`) and `ctrl_cadence_jitter` (that control-channel EWMA); the line itself says "NOT real network jitter". Neither is a live round trip, which is why the stream stats overlay no longer shows this value (the Latency row was removed in #293); the overlay shows FPS only. The console's own round-trip estimate, which it sends in its connection-quality messages, is shown by `PIPE/CONSOLE` (section 9.4).

## 3. Video assembly and FEC

`chiaki_video_receiver_av_packet` (`lib/src/videoreceiver.c:416`) runs on the recv thread for every video packet.

- **Frame boundaries.** A packet with a lower frame index than the current one is dropped as an "old frame packet" (`videoreceiver.c:425-430`). A higher index flushes the previous frame first, then starts a new one (`videoreceiver.c:462-470`). A jump of more than one frame index from the last completed frame is a gap (handled right after, `videoreceiver.c:471` onward).
- **Gap reports to the console.** A gap is held `VIDEO_GAP_REPORT_HOLD_MS` = 24 ms so late packets can fill it, or reported at once if it spans at least `VIDEO_GAP_REPORT_FORCE_SPAN` = 12 frames (`videoreceiver.c:15-17`). Re-reports of a growing range during one stall are rate-limited by `VIDEO_CORRUPT_REPORT_COOLDOWN_MS` = 500 ms, unless the range grew by `VIDEO_CORRUPT_REPORT_GROWTH_BYPASS_SPAN` = 32 frames (`videoreceiver.c:37`, `48`). The pure gap bookkeeping lives in `lib/src/videoreceiver_gap.c` (`chiaki_video_gap_report_update`). `VIDEO_SPAN_SANITY_MAX` = 4096 guards against corrupt sequence state (`videoreceiver.c:19`).
- **Units and FEC.** `lib/src/frameprocessor.c` collects the units of one frame (`chiaki_frame_processor_alloc_frame`, `put_unit`). A flush is allowed once source units plus parity units received reach the number of source units expected (`videoreceiver.c:638`). If all source units are present, the frame is simply concatenated. If some are missing, `chiaki_frame_processor_flush` (`frameprocessor.c:382`) runs FEC (`chiaki_frame_processor_fec`, `frameprocessor.c:315`), which calls `chiaki_fec_decode` (`frameprocessor.c:346`), a Reed-Solomon decode built on Jerasure with a Cauchy matrix (`lib/src/fec.c:5-6`, `14`). Possible results: delivered, FEC-recovered, FEC-failed, failed.
- **Missing references.** After a successful flush, `chiaki_video_receiver_flush_frame` (`videoreceiver.c:643`) parses the H.264 slice. For a P-slice it checks that the frame it points to is still in the receiver's reference table (`have_ref_frame`, `videoreceiver.c:803`). If not, it tries to rewrite the slice to point at an older frame we do have (`chiaki_bitstream_slice_set_reference_frame`, `videoreceiver.c:808-820`). On H.264 that function always returns `false` (`lib/src/bitstream.c:457-458`, the Vita is H.264-only), so this rewrite never succeeds on this build and the code continues to the missing-reference handling in section 4.
- **IDR constants (where they actually live).** `IDR_REQUEST_COOLDOWN_MS` = 100, `IDR_REQUEST_TIMEOUT_MS` = 1000 and `CASCADE_SKIP_THRESHOLD` = 3 are defined at `videoreceiver.c:49-51` (not lines 18-19; those now hold the gap-report constants). Their use is in `video_receiver_maybe_request_idr` (`videoreceiver.c:239`): if a request is pending for more than the timeout, the pending flag is cleared; a new request is sent only if none is pending and at least the cooldown has passed since the last one. A pending request is cleared when an I-slice is received (`videoreceiver.c:782-790`).

## 4. Loss handling

When a frame cannot be used as-is, what happens depends on why.

- **FEC failed.** The frame is discarded, an IDR is requested (reason `"fec_failed"`, `videoreceiver.c:715`), the console is told which frames are corrupt (`report_corrupt_frame_range`, `videoreceiver.c:738`), and `frames_lost` is increased by the span (`videoreceiver.c:739-745`).
- **Missing reference, default behaviour.** `succ` becomes false, so the frame is not given to the decoder; `frames_lost` and `consecutive_missing_ref` go up and an IDR is requested (`videoreceiver.c:821-860`). After `CASCADE_SKIP_THRESHOLD` (3) such frames in a row, `chiaki_video_receiver_flush_frame` skips flush and decode entirely, resets the reference table (`video_receiver_apply_cascade_reset`, `videoreceiver.c:276`) and keeps asking for an IDR (`videoreceiver.c:658-679`).
- **Submit-through-loss (PR #257), config-gated and OFF by default.** If the config key `submit_on_missing_ref` is true and the stream is H.264 with `gaps_in_frame_num_value_allowed_flag == 0` in its SPS (`chiaki_bitstream_h264_drift_safe`, `bitstream.c:463-469`), a missing-reference P-frame is still passed to the decoder (`videoreceiver.c:821-848`). The lost frame was never submitted, so the decoder's newest reference is the last good frame, and the P-frame is decoded against that. The picture may drift until the next I-slice, which is requested at once. The frame is not counted as lost and does not feed the cascade counter. The key defaults to `false` (`vita/src/config.c:57`, parsed at `config.c:401`) and is passed to the library at `vita/src/host.c:387` (`session.c:267`). So on a default install the behaviour in the previous bullet is what runs.
- **What the console is told.** `lib/src/congestioncontrol.c` runs a thread that wakes every `CONGESTION_CONTROL_INTERVAL_MS` = 200 ms, reads and resets the packet statistics, and sends a congestion packet with `received` and `lost` (`congestioncontrol.c:5`). The statistics are filled per frame by `chiaki_frame_processor_report_frame_stats` (`frameprocessor.c:235`) using source units only, never parity (explanation at `frameprocessor.c:249-262`, from PR #213): a frame with all source units counts as lossless; an FEC-recovered frame reports its missing source units as "recovered", not lost; an FEC-failed or skipped frame reports them as lost. In the congestion thread the reported loss is `lost + recovered / 4` (`CONGESTION_FEC_RECOVERED_LOSS_DIVISOR`, so light recoverable loss rounds to zero) and is capped at 10 % of the total (`CONGESTION_MAX_REPORTED_LOSS`, `congestioncontrol.c:11-16`, `44-57`). It matters because the PS5 lowers its bitrate whenever it hears about loss, so inflating the number (for example by counting FEC parity as missing) walks the bitrate down for no reason. A compile-time switch `VITARPS5_CONGESTION_PARITY_INCLUSIVE_RECEIVED` exists for an A/B experiment and is off in the normal build (`congestioncontrol.c:112-116`).
- **Feedback sender.** `lib/src/feedbacksender.c` sends controller state to the console. On Vita it runs at priority 65 (`FEEDBACK_SENDER_THREAD_PRIORITY`, `feedbacksender.c:31`, applied at `413`): below the three 64 threads on purpose, so it never ties with the recv, decode or audio threads.
- **Freeze-then-jump (PR #263): gone.** The presentation hold driven by arrival cadence (the "#262 stale-hold gate") was removed in PR #280 (commit `0e9dd13b`); `vita/src/video.c` no longer contains it. What remains on the display side is the simpler freeze-on-corrupt in section 6.

## 5. Decode (producer / consumer)

All in `vita/src/video.c`.

- **Producer.** The library's video callback `host_video_cb` (`vita/src/host_callbacks.c`) marks the frame corrupt if `frames_lost > 0` or it was a recovered frame (`host_callbacks.c:129`), then calls `vita_h264_decode_frame` (`host_callbacks.c:146`, `video.c:985`) on the recv thread. That function validates the size (rejects under 5 bytes or over slot capacity minus pad), copies the bitstream into the next slot of `decode_queue` plus a 64-byte zero pad, and signals `decode_q_cond`.
- **Queue.** `DECODE_QUEUE_DEPTH` = 4 slots (`video.c:389`), each `DECODE_SLOT_CAPACITY` = 256 KB (`video.c:392`), allocated once in `vita_h264_start` (`video.c:1386` onward). One slot is always held by the decoder, so at most 3 frames wait.
- **When full.** The producer first waits up to 10 ms for the consumer to free a slot (`chiaki_cond_timedwait`, `video.c:1015-1017`). If still full, it drops the oldest queued slot by advancing the head and counts it in `decode_queue_drops` (`video.c:1020-1025`). The comment at `video.c:1007-1013` records the reason for waiting first: dropping a compressed P-frame before decode breaks the decoder's reference chain, which is worse than a short stall.
- **Consumer.** `decode_thread_func` (`video.c:1326`) is created in `vita_h264_start` (`video.c:1447`, named "VitaDecode"). It sets priority `VITA_DECODE_THREAD_PRIORITY` = 64 (`vita/include/video.h:39`) and CPU `USER_1` (`video.c:1330-1331`), waits on `decode_q_cond`, and takes the head slot's data without advancing the head (`video.c:1350`). It runs `decode_frame_now` (`video.c:900`, calls `sceAvcdecDecode` at `video.c:925`), and only afterwards advances `decode_q_head` and signals (`video.c:1370-1380`). Keeping the head put during decode means the producer's "full" test cannot reuse the slot being decoded. Decode always runs, even for frames flagged corrupt, to keep the hardware decoder's reference state in step (`host_callbacks.c:123-127`).
- **Timestamp.** The access unit's presentation timestamp is the frame's running number (upper half 0, lower half the number); before #413 it was `0xFFFFFFFF` in both halves. The decode timestamp (`dts`) is unchanged. The number is read back from the output picture to see which frame came out (section 9.2).
- **Decoder pull (#413, test build, not yet measured on hardware).** The decoder seems to give back at most one picture per `sceAvcdecDecode` call, so each call that returns none leaves one more picture inside for good (reasoned from one log, not proven). After a normal decode that the decoder accepted (return 0 or more, picture or not), `decode_frame_now` calls `decoder_pull_picture`. If the hold (`fed - handed`) is above the pull floor, it makes one extra `sceAvcdecDecode` call with an empty access unit (null buffer, size 0, the same timestamps), the form wiliwili uses when the decoder's input is full (`scripts/psv/ffmpeg/ffmpeg.patch` in xfangfang/wiliwili). At most one pull per fed frame, in the same `mtx` section, into the same `frame_texture`, before anything is published. It is armed only after the decoder has handed back its first picture of the session. The floor starts at 0 and resets per session. The floor also decays (not yet measured on hardware): when 3 seconds (`DECHOLD_PULL_FLOOR_DECAY_US`) have passed since the last floor change, raise or drop, it drops by one step, so it walks down one step per 3-second stretch, and the pull is then tried at the lower level. It never drops below the session's starting floor, the floor the first empty pull of the session set (4 in every log so far; before that first empty pull the limit is 0). Each probe below the starting floor cost a skipped picture on screen, the small hitch every few seconds seen on v0.1.1187. At the starting floor there is no probing in calm play; the starting floor resets per session. The starting-floor limit is not yet measured on hardware. If that pull returns no picture, the floor goes straight back up to the current hold and that counts as a floor change for the timer. A pull is not a fed frame and does not count in `no_output`. Three outcomes:
  - *It returns a picture:* the hold drops by one. The pulled picture replaces the one the normal decode produced, which is therefore never shown (one picture skipped on screen per success; that skip is the catch-up). The picture is published once, with the pulled picture's read-back number (checked like any other).
  - *It returns success with no picture:* the texture was not written, so the normal decode's own result is published as before. The floor rises to the current hold (`PIPE/DECPULL floor=N dir=up frame=F`), so no pull is tried again until the hold climbs above that.
  - *It returns an error:* the texture may be partly written, so nothing from this decode is published and an unclaimed picture is withdrawn like in the negative-return case below. Pulling is turned off for the rest of the session, with one error-level line `PIPE/DECPULL error=0x... frame=F`.
  Whether a pull ever returns a picture, and whether the hold then stays near its start-up value after a burst, is what the hardware log has to show.
- **Handoff to the UI.** `decode_frame_now` stores the corrupt flag with the decoded pixels under `mtx`, then publishes the frame number (`frame_texture_seq`, `incoming_frame_seq`), the decode-done and first-packet stamps and sets `frame_ready_for_display`, all in one critical section under `mtx` (`decode_frame_now`). The UI thread takes the frame in one critical section under the same lock (the claim, section 6), so it can never see these facts half-published or take a frame while the decoder is writing the next one into the same texture.
- **A decode that fails or produces nothing (#418).** The decoder is pointed at `frame_texture`, and a picture decoded earlier may still sit there unclaimed (common: the `overwrites` count on `PIPE/FPS` counts exactly that). Two cases, both in `decode_frame_now`:
  - `sceAvcdecDecode` returns a negative value: the failed decode may have partly written that texture, so if `frame_ready_for_display` is still set it is cleared under `mtx` and counted (`decode_ready_dropped_count`). No trustworthy picture is ready any more; the UI keeps showing what it showed until the next good decode. Before #418 the flag stayed set and the UI would have claimed the damaged texture as a clean picture and promoted it to last-good. Look for `DECODE/ANOM ready_dropped count=N frame=F` (error level; the first 5 per stream, then suppressed, like the other `DECODE/ANOM` lines) and `ready_dropped=N` on the `DECODE/ANOM totals` line written at stream stop. The negative-return line itself is `DECODE/ANOM neg_ret=0x... count=N`. If the flag was not set, nothing changes.
  - The decoder returns success but no picture (`numOfOutput != 1`, `DECODE/ANOM no_output`): the flag is left alone, because nothing was written, so the earlier unclaimed picture is taken to be intact. This happens 4 to 5 times at the start of every session in every hardware log.
  - The early return "Video decode buffer too small" never calls the decoder, so the texture and the flag are untouched. The frame is still dropped, but the drop is now logged and counted (`DECODE/ANOM buf_too_small`, section 9.2); before, it only went to the console print, which never reaches the log.
  - The pull call in the decoder-pull bullet above (when it returns an error) follows the same rule as a failed normal decode.
  Read from the code, not observed: no hardware log contains a negative decode return (`neg_ret`), so the ready-dropped path has never run on hardware.

## 6. Display and audio

- **Vblank wait.** The `draw_ui()` loop in `ui.c` is the only place that switches vita2d's vblank wait. It turns it off when the loop takes the stream branch (`is_streaming` true, before `vita_video_render_latest_frame()` swaps) and on again when it takes any other branch. `vita_h264_start` and `vita_h264_stop` no longer touch it.
- **UI thread.** `vita_video_render_latest_frame` (`video.c:1105`) returns at once, without any lock, if streaming is not active or `frame_ready_for_display` is false. Otherwise it **claims the frame** (#416): one critical section under `mtx` that re-checks the flag (false under the lock is treated as a miss; it has two causes: `vita_h264_stop` cleared it, or `decode_frame_now` withdrew the picture after a failed decode, section 5), clears it, reads the corrupt flag, the two stamps, the picture number and the PIPE/PRESS pair, and, if the frame is clean, does the texture swap. Because `decode_frame_now` holds the same `mtx` for the whole decode and publish, the decoder can never complete a frame in the middle of the claim: the facts read belong to the picture the swap hands to the draw, the flag cannot be left set for a picture already taken, and a picture overwritten before it was claimed is counted in `frame_overwrite_count`. The claim holds `mtx` once per frame, clean or corrupt, and contains no blocking call, log call, allocation or clock read; the draw and the GPU wait happen after it, without the lock. Before #416 the flag was cleared long before the lock was taken, which left a window in which the UI could show the picture after the one it had claimed with the flag still set and `frame_texture` pointing at the previously shown picture (see 9.10). It then picks a texture:
  - clean frame: `promote_decoded_frame_to_last_good` swaps the two fixed textures `frame_texture` and `last_good_texture` (a pointer swap, with their picture numbers, inside the claim, no copy), and the new picture is shown;
  - corrupt frame and a last-good texture exists and fewer than `FREEZE_MAX_STREAK` = 8 corrupt frames in a row (`video.c:179`): the last good picture is shown again instead (`video.c:1200-1208`);
  - corrupt for 8 in a row, or no last-good texture: the decoded (possibly broken) frame is shown, so the picture always resumes (`video.c:1219-1224`). **This draw is made without `mtx`, on purpose (#418, decision: leave it).** `frame_texture` stays the decoder's target, so the decode thread can start the next decode while the GPU is still reading it, and the viewer could see one torn picture. It is not a memory-safety problem: both textures are fixed allocations that live until `vita_h264_cleanup`, so the worst case is pixels overwritten under a read, on a picture already flagged corrupt, shown only after 8 corrupt frames in a row (or when the second texture failed to allocate and there is no last-good texture). Closing it would mean holding `mtx` across the draw and the GPU wait, which stalls the decode thread exactly during sustained loss, or a third texture of about 2 MB. Read from the code; not observed on hardware.
  It then draws (`draw_streaming`), calls `vita2d_wait_rendering_done()` and `vita2d_swap_buffers()` (`video.c:1246-1247`). The Vita does no local frame pacing (the Force 30 FPS Output setting was removed in #473): every claimed frame is drawn, and the fps is set only by what the console is asked for.
- **Audio (#416).** Sound output is on its own thread; the receive thread only hands audio over. None of this has been measured on hardware yet: what follows is what the code does and what it is meant to achieve.
  - **Path.** Audio packets take the recv-thread path (`takion_handle_packet_av`, then `stream_connection_takion_av` and `chiaki_audio_receiver_av_packet`, then `chiaki_audio_receiver_frame`), and the Opus decoder callback `chiaki_opus_decoder_frame` (`lib/src/opusdecoder.c`) runs `opus_decode` and calls `vita_audio_cb` (`vita/src/audio.c`), still on the recv thread. **Opus decoding still runs on the recv thread**; only the sound output moved.
  - **Receive thread (`vita_audio_cb`).** Copies the decoded frame into a hand-off queue (`audio_queue_push`, `vita/src/audio_queue.c`) under `audio_mtx`, signals `audio_cond` once at least one device buffer is queued (the audio thread's gate decides whether it may proceed), and returns. The mutex is held for one bounded frame copy plus the catch-up bookkeeping. It never calls `sceAudioOutOutput`, never waits for the audio thread or for room in the queue (a full queue is handled by the catch-up rule, below), never allocates, and no longer changes its own priority or core. A frame whose sample count differs from the first frame's is logged and dropped.
  - **One-time init, first audio frame.** `audio_start` runs on the recv thread when the first frame arrives (the frame size is only known then). It sizes the device buffer as the smallest whole number of frames that is a multiple of 64 samples (2 frames of 480 samples), allocates the queue storage and the audio thread's rotation of `AUDIO_PLAY_BUFFERS` = 4 play buffers (4 device buffers) once, calls `sceAudioOutSetConfig`, and creates the thread. If anything fails it undoes it, logs an error once and audio stays off for the session (`audio_disabled`). There is no allocation per frame afterwards.
  - **Audio thread.** `audio_thread_func`, created in `audio_start` and named "VitaAudio". It sets itself to priority `VITA_AUDIO_THREAD_PRIORITY` = 64 (`vita/include/audio.h`) and CPU `USER_2`. Its loop waits on `audio_cond` until the queue's gate (`audio_queue_may_pop`) allows one device buffer, copies exactly one device buffer into the next play buffer of the rotation under `audio_mtx`, releases the mutex, reads `sceAudioOutGetRestSample` once (a statistic only, nothing decides on it), then calls `sceAudioOutOutput`, which blocks until the hardware can take the data and is the pacing. The mutex is never held across that call. If the gate does not allow it the thread waits and writes nothing. It exits promptly when told to, without draining the queue. **Play-buffer rotation.** The play buffers rotate so a block handed to `sceAudioOutOutput` is not written again until 3 further calls (60 ms at 20 ms per block) have gone by, the same distance as the 4-device-buffer ring before #416. Why: the SDK header does not say the call copies the data, and the device still reports 64 to 704 of 960 samples outstanding when the call returns (`rest_min`/`rest_max`, build 0.1.1179 log), while the audio thread used to refill the single play buffer about 90 microseconds after the call returned. If the device reads from our pointer, that would overwrite sound it is playing. This is a suspected cause of the garbled sound heard on build 0.1.1179, not confirmed on hardware.
  - **Start level.** The gate is: not primed (a new queue) only once the start level is queued, which primes it for good; primed, whenever one device buffer is queued. The start level is one device buffer plus `AUDIO_REFILL_CUSHION_MS` = 30 ms (`vita/include/audio.h`; a start cushion only, the name is historical), converted to frames from the real frame size and rate (3 frames, so 5 frames or 50 ms for 480 samples at 48 kHz; at least 1 frame of cushion). Playback therefore starts only with the cushion queued, and once playing the cushion absorbs arrival jitter. The added delay is about 30 ms compared with build 0.1.1175. **No re-arm.** Builds 0.1.1177 and 0.1.1179 also held output for the start level again whenever the thread had slept and the rest sample read exactly 0; that was removed in #416 round 5, for two reasons. (1) A rest of 0 does not mean a gap has been heard: in the four pre-#416 logs the rest sample read 0 before 100 percent of output calls (`rest_min=0 rest_max=0 out_dry=out_calls`) and that sound was acceptable. (2) In the 0.1.1179 log the hold fired 32 times, several after waits of only 13 to 17 ms (`out_gap_max_us`), each adding tens of ms of silence. It is also unnecessary, reasoned and not measured: when the queue runs out during an arrival gap of G ms, the G ms of sound that then arrives leaves the queue G ms full by itself, so the level rebuilds without any hold. That argument covers sound that arrives late, not sound that is lost. **Lost frames (#440).** Measured in log `37535415638_vitarps5-testing.log` (build from main f19ddbce, about 3 minutes): `q_avg` was 6 to 7 at the start and fell to about 1.5 after the first few `frames_missing`, then stayed there. `out_dry` read about 800 in long stretches, with `waits` rising. Catch-up ran only twice, each after a 0.7 to 0.9 s freeze, and is not the cause. A lost frame was simply absent, so each loss lowered the level by one frame and nothing raised it again; once the cushion was gone every arrival delay was heard. **Fix: concealment.** When `chiaki_audio_receiver_frame` accepts an audio frame whose index jumped, it first hands the audio sink one "lost frame" call per missing frame (`frame_cb` with `buf == NULL`, `buf_size == 0`), then the frame that arrived, so order is kept. `chiaki_opus_decoder_frame` turns such a call into one Opus packet-loss-concealment frame (`opus_decode` with no data, the header's frame size), which goes through `vita_audio_cb` like any other frame, so the level stays where it was. At most `CHIAKI_AUDIO_RECEIVER_CONCEAL_MAX_FRAMES` = 5 frames are concealed per jump (`lib/include/chiaki/audioreceiver.h`): 5 frames is the start level, the cushion being kept; a longer jump is a stall, not scattered loss, and concealing more would only push the queue toward the 10-frame catch-up bound once the real burst arrives, where it is thrown away; and Opus concealment fades toward silence over long runs anyway. Haptics are never concealed. The gap is now computed in every build (it was probe-only). The count is `concealed` on `PIPE/AUDIO`. **Copies first (#445).** Each packet carries its own frame plus copies of the two frames before it. The redundant copies in each packet are fed before the packet's own frames, so a single lost packet, or packets reordered up to two deep, is repaired with real audio; concealment now covers only holes deeper than the copies (3 or more consecutive lost packets). **The fix itself is not yet measured on hardware.** Reasoning and measurement: 9.9, dated records.
  - **Catch-up rule.** After each push, if more than the bound is queued, the oldest frames are dropped so exactly the start level of the newest remains (`audio_queue_push`). The bound is `AUDIO_CATCHUP_BOUND_MS` = 100 ms, converted to frames from the real frame size and rate (10 frames for 480 samples at 48 kHz) and never below the start level plus one frame; the kept amount is the start level (5 frames, 50 ms), so a catch-up does not leave playback without a cushion; the ring holds the bound plus one frame, so a push can never overflow. Reasoned, not measured on this build: 100 ms is above the arrival gaps seen in earlier hardware logs of otherwise good runs (routinely 50 to 60 ms, up to 88 ms, so up to about 9 frames arriving at once) and about what the picture already waits in the decoder (`PIPE/DECHOLD` holds 4 to 5 frames, 65 to 80 ms); the full reasoning is the comment on `AUDIO_CATCHUP_BOUND_MS`. What a listener gets after a hiccup: the burst that arrives after a stall does not play back late; the old part is dropped (a skip in the sound) and playback continues from the newest audio.
  - **Why it exists.** Measured on the #413 probes build, before this change: `sceAudioOutOutput` took roughly 70 to 85 percent of the receive thread's elapsed time, so the thread could keep pace with the stream but not go faster; after a stream gap of about 0.45 s, 280 to 330 KB (about 0.55 to 0.6 s of stream) stayed unread in the socket for more than 80 s (`PIPE/SOCKQ`), and 15 to 30 KB was always waiting in good gameplay. The old ring's catch-up never ran (section 9.3). The probes for judging the change are in 9.6 to 9.9.
- **Thread priorities in one place.** `host.c` logs `PIPE/PRIORITY decode=64 audio=64 recv=64 feedback=65 input=96` (`host.c:514`). `audio=64` is `VITA_AUDIO_THREAD_PRIORITY`, applied by the VitaAudio thread to itself. The three media threads are each pinned to their own core: recv `USER_0`, VitaDecode `USER_1`, VitaAudio `USER_2`. Lower number means higher priority on Vita.

## 7. Teardown order

`host_shutdown_media_pipeline` (`vita/src/host_lifecycle.c:10`) must run in this order:

1. `context.stream.is_streaming = false`, then `vita_h264_stop()`.
2. `sceKernelDelayThread(2000)`.
3. `chiaki_opus_decoder_fini`, then `vita_h264_cleanup()` (frees the decoder and textures, `video.c:827`), then `vita_audio_cleanup()` (stops and joins the audio thread, then frees its buffers; below).

Inside `vita_h264_stop`:

- It clears `active_video_thread` first. This is what makes `vita_video_render_latest_frame` bail out (the teardown gate at its top); `is_streaming = false` alone is not enough because the UI thread only reads it on its next loop.
- It signals the decode thread to exit and **joins** it, so no `sceAvcdecDecode` is running on a decoder that is about to be freed.
- It frees the queue slots, then **waits, without a bound,** until `ui_render_in_progress` is clear, and only then calls `chiaki_mutex_fini(&mtx)` (#418). The flags are exact, not a timing argument: `vita_video_render_latest_frame` sets `ui_render_in_progress`, then runs a full memory barrier (`__sync_synchronize()`), then reads `active_video_thread`; `vita_h264_stop` clears `active_video_thread`, then runs the same barrier, and only later reads `ui_render_in_progress`. So either the render pass sees teardown and returns without touching `mtx`, or the stop path sees the pass in progress and waits for it. Before #418 the wait gave up after 50 ms and destroyed `mtx` anyway; a render pass stalled longer than that would have locked a destroyed mutex and could have drawn a texture that `host_shutdown_media_pipeline` frees 2 ms later. Giving up is a use of a destroyed lock and a freed texture, so the wait has no bound and a stuck wait is made loud instead: after `UI_RENDER_QUIESCENCE_WARN_US` = 50 ms it logs `VIDEO/STOP ui_wait still waiting for the UI thread to leave the render call elapsed_us=N` (error level), repeated every `UI_RENDER_QUIESCENCE_REPORT_INTERVAL_US` = 1 s, and when the wait ends after having warned it logs `VIDEO/STOP ui_wait done elapsed_us=N`. A wait under 50 ms logs nothing. The wait polls every `UI_RENDER_QUIESCENCE_POLL_US` = 1 ms. It can only end because the UI thread always leaves the render call: it blocks only on `mtx` (no thread holds it by then: the decode thread was joined, and nothing else takes it), the vita2d GPU wait and swap, and the log mutex (held for short stretches only).

Inside `vita_audio_cleanup` (`vita/src/audio.c`, #416), if the audio thread was started: it takes `audio_mtx`, sets `audio_exit`, signals `audio_cond`, releases the mutex and **joins** the thread (`chiaki_thread_join`). Only then does it log the session stats, free the queue storage and the play buffer, destroy the mutex and condition, and reset its state. The join comes first because the audio thread uses all of those, and it may be inside `sceAudioOutOutput` (it sees the exit request when that call returns, at most about one device buffer, 20 ms for 480-sample frames). Same discipline as `vita_h264_stop()`: signal, join, then free.

Why the receive thread cannot still be calling `vita_audio_cb` (which locks `audio_mtx` and writes into the queue) when this runs: the call comes from `host_handle_quit_event` (`host_quit.c`) on `CHIAKI_EVENT_QUIT`, and `session_thread_func` (`lib/src/session.c`) sends that event only after `chiaki_stream_connection_run` has returned; on its way out that function calls `chiaki_takion_close` (`streamconnection.c`, label `close_takion`), which stops and **joins** the Takion thread (`takion.c`). The other caller, in the failure path of `host_stream` (`host.c`), runs only when the session did not start, so no Takion thread exists.

Why the order matters: the decode thread writes into `frame_texture`, the UI thread draws from it and both take `mtx`. Freeing the texture or destroying the mutex while either thread is inside it is a use-after-free (destroying a mutex a thread holds is undefined on the Vita kernel). The comments in `vita_h264_stop` call the order "load-bearing".

**What has and has not been seen (#418).** None of the three situations above (the cap-release draw tearing, a failed decode with a picture unclaimed, a render pass outlasting the stop path) has been seen in a hardware log; all three are read from the code. The seven logs in the repo root (`*_vitarps5-testing.log`, checked with `grep -a`) contain no stream stop at all: none has `decode thread exiting` or `DECODE/ANOM totals`, so they say nothing about the stop path either way. On a future log, `VIDEO/STOP ui_wait` lines mean the UI thread was slow to leave the render call; their absence at a stop that did log `DECODE/ANOM totals` means the wait ended in under 50 ms.

## 8. Recovery after the stream dies

### 8.1 What the library does and does not do

When the transport gives up (for example the ENOBUFS budget in section 2 is exhausted) and the console did not disconnect us, the session ends with `CHIAKI_QUIT_REASON_STREAM_CONNECTION_TRANSPORT_FAILED` (`lib/src/session.c:889-897`). The library no longer tries a soft restart on its own: the old restart ladder and the `CHIAKI_EVENT_STREAM_RESTARTING` event were removed in PR #274 (commit `789415ed`), because a soft restart reuses a control connection the console never releases and every field log showed it timing out (`session.c:793-803`). A restart that someone asks for explicitly through `chiaki_session_request_stream_restart` (`session.c:410`) is still honoured.

On the Vita app, the only code that asks for such a restart is `request_stream_restart` / `request_stream_restart_coordinated` in `vita/src/host_recovery.c:30`, `91`. Their only callers are the stages inside `host_recovery_handle_post_reconnect_degraded_mode` (`host_recovery.c:257`, `285`), and that function returns at its first guard because `post_reconnect_window_until_us` is never set to a non-zero value anywhere (`host_recovery.c:165-180`, writers at `host_callbacks.c:26` and `host_metrics.c:117` both write 0). In practice nothing on `main` requests a soft restart.

### 8.2 The quit handler

`host_handle_quit_event` (`vita/src/host_quit.c:42`) runs on the dying session's own thread. In order:

1. It snapshots everything that decides finalize and recovery before touching the media pipeline, because the pipeline shutdown clears some of it (`host_quit.c:53-60`, `83-90`): `had_streamed`, `fast_restart_active`, `recovery_active`, the attempt counter and the release-poll counter.
2. It decides whether to recover: `recovery_trigger` is true for a transport death (`host_quit.c:102-109`), for a user resync (debug builds), or for a quit that happens while a recovery is already active and the reason is RP_IN_USE or a retryable one. A user stop never triggers it. Recovery is scheduled while `loss_retry_attempts < LOSS_RETRY_MAX_ATTEMPTS` = 2 (`host_quit.c:110`, `vita/include/host_constants.h:4`).
3. It publishes `recovery_active` before the session is marked gone, so `host_in_active_use()` stays true during the hand-off (`host_quit.c:124`, `host.c:109-118`), then calls `host_shutdown_media_pipeline()` (`host_quit.c:125`), then turns the Reconnecting overlay back on immediately so the UI never flashes the main menu (`host_quit.c:128-131`).
4. It cannot join its own thread, so it sets `session_finalize_pending = true` and `session_init = false` and returns (`host_quit.c:139-143`). The UI thread does the join and `chiaki_session_fini` in `host_finalize_deferred_session` (`vita/src/host_lifecycle.c:63`), called from the top of the UI loop (`vita/src/ui.c:520-522`).
5. It stores the schedule: `loss_retry_ready_us`, the attempt count, the cause string, and sets `loss_retry_pending = true` after a memory barrier so the UI thread can never see the pending flag before the finalize flag (`host_quit.c:341-385`, barrier at `384`).

### 8.3 The UI loop starts the reconnect

In `vita/src/ui.c:566-586` the UI thread starts the new connection when all of these hold: `recovery_active`, `loss_retry_pending`, the old session is finalized (`!session_finalize_pending && !session_init`), no connection thread is running, and the clock has passed `loss_retry_ready_us`. If there is no active host or the connection thread cannot start, it calls `host_recovery_abort` (`host_quit.c:418`), which clears all recovery state and shows "Could not reconnect to console". The screen is the Reconnecting screen for the whole episode (`ui.c:665-668`).

The reconnect always uses the user's Latency Mode bitrate from `host_default_video_profile` (`host_quit.c:92-95`, `368`; `host.c:195-210`, `309-319`), never the dying session's bitrate. That is the same start bitrate as a first connect, so "Retrying at X Mbps" shows the user's own choice.

The stream profile (`host_default_video_profile`, `host.c`) takes the resolution from Quality Preset and the frame rate from FPS Target, with one exception: at 1080p the console is always asked for 30 fps, whatever FPS Target says, because the Vita decoder tops out at about 42 fps at 1080p and a 60 fps request builds an ever-growing backlog (#456). The stored FPS Target is not changed, so it applies again at the other resolutions. `host_stream()` logs `1080p fps override: resolution=1080p fps_setting=<30|60> requested_fps=30` once per stream start at 1080p; `profile.max_fps`, `negotiated_fps` and `target_fps` (overlay, metrics, recovery, loss profile) all carry the 30. Reconnects go through `host_stream()` again, so they follow the same rule. 720p and 1080p reach the console as chosen; nothing downgrades them to 540p any more (#473).

The start bitrate (first connect and every recovery reconnect) comes from the Settings Latency Mode, not from the resolution preset: Ultra Low 1500, Low 2500, Balanced 3500, High 4500, Max 6000 kbps (`latency_policy_kbps`, `vita/src/latency_policy.c:13-27`). Default is Max (`config.c:57`). On the Internet/PSN path the lower of the mode's value and `PSN_REMOTE_BITRATE_CAP_KBPS` = 3500 wins (`latency_policy_start_kbps`, `latency_policy.c:29-40`; applied in `host.c:208`); the log line `Bitrate policy: latency_mode=<mode> (<kbps> kbps @ WxH)` shows the uncapped value, and a second line shows the clamp (`host.c:310-314`). The value goes out in the `RP-StartBitrate` header and the LaunchSpec unchanged (`lib/src/ctrl.c`, `lib/src/streamconnection.c`). The same effective bitrate is the target that `host_adjust_loss_profile_with_metrics` compares the measured bitrate against (`host_loss_profile.c:111-116`), so a capped PSN session is not read as under-delivering. Before #420 this setting only tuned loss thresholds and every session asked for the preset's 6000 kbps. A one-time migration (`migrate_latency_mode`, `config.c:557-562`, marker `latency_mode_migration` in `[settings]`, version `LATENCY_MODE_MIGRATION_CURRENT`) moved every existing saved value to Max the first time #420 loaded, since the old value had no effect; fresh installs and unreadable configs are marked as already migrated (`config.c:607`, `617`, `625`), so a later choice sticks.

### 8.4 State that survives `host_stream()`

`recovery_active`, the attempt count, the release-poll count and the overlay start time are not reset when `host_stream()` starts a new connect (`host.c:278-279` reads them). They are cleared only when the new session reports `CHIAKI_EVENT_CONNECTED` (`host_callbacks.c:59-74`, "Recovery complete"), on abort or on exhaustion (or on a user cancel, which nothing triggers today). The overlay itself is cleared on the first video frame (`host_callbacks.c:114-122`). A later drop after a successful recovery therefore starts a new episode with the full budget of 2.

### 8.5 Timing: the first attempt and the console-release polls (PR #279)

- **First attempt after a transport death.** `ready_us = now + RECOVERY_CONSOLE_RELEASE_DELAY_US`, which is `RETRY_HOLDOFF_RP_IN_USE_MS` = 9000 ms (`host_quit.c:19`, `24`, `341`). The delay is still 9 s here; PR #279 did not change it. (A debug-widget resync skips it: `ready_us = now`, `host_quit.c:342-343`.)
- **If the console still refuses (RP_IN_USE) during recovery.** Instead of waiting out another fixed 9 s, the handler sets `release_poll` (`host_quit.c:114-115`) and schedules the next probe `RECOVERY_RELEASE_POLL_INTERVAL_US` = 1 s later (`host_quit.c:31`, `194-196`, `344-345`). The code comment (`host_quit.c:25-30`) notes a refused probe itself costs about 250 ms. Up to `RECOVERY_RELEASE_POLL_MAX` = 8 polls (`host_quit.c:32`). A poll does not use up the attempt budget and the Reconnecting screen's "Attempt N" does not change (`host_quit.c:364-366`). Each poll logs `Release wait: RP_IN_USE poll n/8 ...` (`host_quit.c:350-355`).
- **After 8 polls.** The next refusal falls back to the old behaviour: it counts as an attempt, logs "polls exhausted ... falling back to 9000 ms holdoff" (`host_quit.c:356-361`), and the holdoff of 9000 ms is armed (`host_quit.c:199-209`). When attempts reach 2, recovery is exhausted: `recovery_exhausted` shows the "Could not reconnect to console" banner and hint and the app lands on the main menu (`host_quit.c:299-306`, `386-395`).
- **Cancel.** The Reconnecting screen has no input and cannot be cancelled (SPEC 3.4); a recovery ends by succeeding, by abort or by exhaustion. There is no user cancel of a recovery (`host_recovery_cancel_by_user` was removed in #382; nothing had called it since the Reconnecting screen was rebuilt in #301). A connect that has not reached `session_init` is still cancelled inside `host_stream()` by the barrier check at `host.c:521-527`.

### 8.6 RP_IN_USE outside a recovery (PR #215 path)

When the console answers a plain user connect with RP_IN_USE, `arm_rp_in_use_auto_retry` (`host_quit.c:176-178`) arms one automatic retry: `rp_in_use_retry_at_us` = now + `RP_IN_USE_AUTO_RETRY_DELAY_US` (6 s, `host_quit.c:36`), or later if a cooldown is still running (`host_quit.c:266-268`). `rp_in_use_retry_used` makes it fire once. The UI loop starts it only when the screen is the main menu and no connection is in flight, and it restores the user's PSN-versus-LAN choice (`ui.c:538-553`). Inside a recovery this path is off (`!restart_context`) because the recovery logic above handles RP_IN_USE.

The post-stop guard applies when the user ends a stream: after a clean disconnect the console acknowledged, a new connect is blocked for `POST_STOP_GUARD_DISCONNECT_ACKED_US` = 2 s; sent but not acknowledged, or never sent after the stream was live, 8 s (`POST_STOP_GUARD_DISCONNECT_UNACKED_US`); a connect cancelled before any stream started has no guard (`host_quit.c:34-35`, `229-258`).

## 9. Delay probes (#413)

Log lines added to find where the delay between a button press and the changed picture lives. They only measure: nothing here changes what is sent or when. All of them except `PIPE/SPS` and `PIPE/SPS_REPEAT` (section 9.5, printed whatever `show_latency` says) print only when `show_latency` is on, once per window next to `PIPE/LATENCY`, `PIPE/INPUT`, `PIPE/DISPLAY` and `PIPE/FPS` (`host_metrics_update_latency`, `vita/src/host_metrics.c`). Each log line has its own subsection below.

### 9.1 `PIPE/PRESS` and `PIPE/PRESS_SAMPLE`: from a button press to the changed picture

**What it measures.** For a button press, how long until the console's answer is on the Vita screen, split into four points. The use: navigate a quiet PS5 menu (Settings) at one to two presses a second; the first big video frame after each press is the menu move. Two log lines come out: one `PIPE/PRESS` summary per window and one `PIPE/PRESS_SAMPLE` per completed sample.

**Clock.** Everything is `sceKernelGetProcessTimeWide()` in microseconds, the same clock as the other `PIPE/` lines. The library's millisecond stamps (`chiaki_time_now_monotonic_ms()`) are the same clock cut to whole milliseconds (`vita/src/video.c`, comment in `vita_video_render_latest_frame`).

**Start point (press sent).** `feedback_sender_thread_func` in `lib/src/feedbacksender.c`: on a wake where the history packet goes out and at least one digital button changed from released to pressed, the time right after the send is stored with a press counter that only goes up. Releases, sticks, touches and the analog L2/R2 values do not count; a press and release gives one event. The receive thread reads it with `chiaki_feedback_sender_read_press_stamp` without any lock (a seqlock, so it never sees a count paired with another press's time). Only the newest press is stored, so two presses between two polls (one frame, about 16 ms) leave one unknown press, counted as `unseen`.

**The four points**, each in microseconds since the press was sent, for the same video frame (the "jump frame"):

| Field | End point | Hook |
|---|---|---|
| `first_us` | The frame's first packet was read by the receive thread. Only known to 1 ms: the library stamps whole milliseconds, so this reads up to 999 us early. | `cur_frame_first_packet_ms` in `lib/src/videoreceiver.c`, passed in as `frame_first_packet_ms` |
| `assembled_us` | The assembled frame reached the decode hand-off. | `press_meter_observe_frame`, called at the top of `vita_h264_decode_frame` (`vita/src/video.c`); one clock read per frame was added there |
| `decoded_us` | Decoding of the frame that was shown finished. | The decode-done stamp in `decode_frame_now` (`vita/src/video.c`), the same value `PIPE/DISPLAY` uses for its pickup span |
| `shown_us` | The swap that put the picture on screen. | The clock read right after `vita2d_swap_buffers()` in `vita_video_render_latest_frame` (no extra read) |

**Detector** (`vita/src/press_meter.c`, pure logic, tested natively; constants in `vita/include/press_meter.h`). It runs on the receive thread, with integer compares only.

- **Queue.** Presses wait in a FIFO of `PRESS_METER_QUEUE_DEPTH` = 4. A press finding it full is refused and counted (`full`). Each press expires `PRESS_METER_EXPIRY_US` = 1 s after it was sent (`expired`), oldest first.
- **Quiet reference.** The second largest of the last `PRESS_METER_QUIET_WINDOW` = 8 calm frames (133 ms at 60 fps). Second largest, so one outlier frame cannot hide an answer; 8 frames, so it follows the picture within about a tenth of a second. The window must be full before any jump counts.
- **Jump.** Outside a burst, a frame of at least `PRESS_METER_JUMP_RATIO` = 3 times the reference AND at least `PRESS_METER_JUMP_MIN_EXTRA_BYTES` = 1536 bytes more. Corrupt frames are ignored entirely.
- **Burst.** Every jump (matched or not) starts a burst, which stays until `PRESS_METER_BURST_END_CALM_FRAMES` = 8 calm frames in a row (133 ms). A frame in a burst is calm when it is below the reference frozen at burst start plus `PRESS_METER_CALM_MARGIN_BYTES` = 1024. Frames in a burst are never jumps and only calm ones enter the quiet window, so the tail of one menu move can neither become the next press's sample nor raise the reference. A burst longer than `PRESS_METER_BURST_MAX_US` = 2 s is cut off and the quiet window is rebuilt from scratch, so a picture that stays busier cannot blind the meter for good.
- **Matching rule.** A jump is matched to the OLDEST waiting press that is eligible. A press is eligible when it was sent no later (compared in whole milliseconds) than the jump frame's first packet; a frame already under way when the press was sent cannot be its answer. `waiting` on the sample is the number of eligible presses, so `waiting=1` means no other press could have been the cause. With `waiting>1` the answer may belong to a younger press (the oldest may have had no answer at all, e.g. a press at the end of a list); the oldest is picked because answers take 150-650 ms against presses 500-1000 ms apart, so the oldest is the likelier. The other eligible presses stay in the queue.
- **Presses inside a burst.** A press sent while a burst is running is queued like any other but counted (`inburst`) and marked `inburst=1` on its sample. Its answer arrives at least 150 ms later, usually after the burst has ended, so it is normally measured. If instead its answer merges into the running burst it cannot be seen (no jump is allowed inside a burst); the press then expires, or, worse, a later jump is taken for it. That is why the mark exists: drop `inburst=1` samples when in doubt.
- **No match.** A jump with no eligible waiting press (nobody asked, or the frame began before the press) is counted as `unmatched`. It still starts a burst.

**Which frame is shown.** The jump frame may never reach the screen: the decode queue can drop it, a newer decoded frame can replace it, or the freeze-on-corrupt path can show the last good picture instead. Frames carry a running number. The number of the picture in `frame_texture` is the one the decoder reports back for it (`PIPE/DECHOLD`, section 9.2) when that read-back is good, and the number that was fed in when it is not; so if the decoder holds frames back, `decoded_us` and `shown_us` still belong to the frame that is really on screen. A jump completes at the first swap that presents a freshly decoded picture whose number is the jump frame's or newer; then `decoded_us` is that picture's decode-done. A pass that only repeats an older picture completes nothing.

**Several jumps in flight.** Answers can be 300 ms apart while a picture is shown up to about 150 ms after it is assembled, so more than one armed jump can be outstanding. They go from the receive thread to the UI thread through a single-producer / single-consumer ring of `PRESS_JUMP_RING_DEPTH` = 8 slots in `vita/src/video.c`, no lock: the receive thread writes a slot and then raises `press_jump_head`; the UI thread reads a slot, completes it and then raises `press_jump_tail`; the receive thread only writes a slot that the tail has already released. At one swap every armed jump whose frame number the shown picture has reached completes, oldest first (they then share the same `decoded_us` and `shown_us` basis, which is the picture that was really shown). A jump whose frame is still ahead of the picture stays armed. If the ring is full the new jump is dropped and counted in `lost`.

**`PIPE/PRESS` (one per window, printed even when empty).**

| Field | Meaning |
|---|---|
| `presses` | Presses sent this window. |
| `n` | Completed samples this window (all of them, listed or not). |
| `amb` | Samples with `waiting>1` this window. |
| `order_err` | Samples whose points were out of order (they should satisfy 0 <= first <= assembled <= decoded <= shown). Nothing is clamped. |
| `expired` | Presses that saw no jump within the expiry. |
| `full` | Presses refused because the queue was full. |
| `inburst` | Presses sent while a burst was running (they are still measured; see above). |
| `unseen` | Presses that fell between two polls of the press stamp (their times are unknown). |
| `unmatched` | Jumps with no eligible waiting press. |
| `lost` | Jumps dropped because the UI thread had not yet shown the earlier ones (ring full). |
| `sample_overflow` | Completed samples beyond the per-window list of `PRESS_WINDOW_SAMPLE_CAP` = 8 (counted in `n`, no `PIPE/PRESS_SAMPLE` line). |
| `presses_total`, `samples_total` | Session running totals. |

Example: `PIPE/PRESS presses=2 n=1 amb=0 order_err=0 expired=0 full=0 inburst=1 unseen=0 unmatched=0 lost=0 sample_overflow=0 presses_total=21 samples_total=15`

Removed from the old line (they were the newest sample only, now carried in full by `PIPE/PRESS_SAMPLE`): `first_us`, `assembled_us`, `decoded_us`, `shown_us`, `first_max_us`, `shown_max_us`, `frame_bytes`, `quiet_bytes`. `overlap` is gone too: presses are no longer ignored while another waits; the cases it covered are now `full`, `inburst` and `unseen`.

**`PIPE/PRESS_SAMPLE` (one per completed sample).** Printed on the UI thread at window close, from a fixed per-window buffer, under the same `show_latency` gate; never from the receive or decode thread. The window's first samples come out in completion order.

| Field | Meaning |
|---|---|
| `press` | The sender's press number (the same counter that `presses_total` ends at), so a missing number in a log shows a lost sample or line. |
| `first_us`, `assembled_us`, `decoded_us`, `shown_us` | The four points above. |
| `frame_bytes`, `quiet_bytes` | Size of the jump frame and the quiet reference at that moment. |
| `waiting` | Presses eligible for this frame when it was matched; 1 = unambiguous. |
| `inburst` | 1 when the matched press was sent while a burst was running. |
| `order_ok` | 1 when 0 <= first <= assembled <= decoded <= shown (first known). |

Example: `PIPE/PRESS_SAMPLE press=15 first_us=312000 assembled_us=330510 decoded_us=455720 shown_us=468330 frame_bytes=4175 quiet_bytes=520 waiting=1 inburst=1 order_ok=1`

**Picking trustworthy samples.** Keep lines with `waiting=1` and `order_ok=1`; for the strictest set also `inburst=0`. `frame_bytes` should be several times `quiet_bytes`. To see how much was left out, compare `presses_total` with the number of samples kept, and read `expired`, `inburst`, `unmatched` and `amb` over the run. A ragged number sequence in `press=` means the log dropped lines (see below).

**What the first hardware log showed** (log 26017450183, PS5 menu at one to two presses a second, 60 fps; this was the old one-slot detector). Of 45 presses in the first session only 12 became samples. Measured: the surviving samples had `first_us` 155-646 ms and `shown_us` 255-820 ms, jump frames of 3033-7995 bytes and quiet references of 39-1612 bytes; the visible lines of that session summed to 10 expired and 14 overlapped presses; the 45 presses are 12 samples plus at least 10 expired plus at least 14 overlapped, with the rest in lines the log lost. Reasoned (the log has no per-frame sizes): (1) Overlap: a press waits 150-650 ms for its answer and presses come 500-1000 ms apart, so a second press arrives while the first waits in roughly a third to nearly all cases; the single slot dropped every one of them, and a press with no answer held the slot for 1.5 s. (2) Quiet reference: it was the largest of 16 frames and the frames of the menu move itself (windows with one sample show `lg=22..26` frames above the previous window's average, i.e. about 0.4 s, and `fsz` maxima of 5-8 KB) were pushed into it, so for the move plus 16 frames (about 0.7 s) a 3-8 KB answer needed 9-24 KB to count and could not be seen; any press answered within 0.7 s of the previous answer, which at 500-700 ms spacing is most of them, expired. An outlier of 1612 bytes would by itself require 4836 bytes: three of the eight answers in that session (3033, 3955, 4175) are below that. (3) Expiry: the 10 expired presses cannot be split into "no answer" (end of a list) and "answer not seen"; the log cannot separate them. (4) Reporting: `PIPE/PRESS` printed only the newest sample, but no visible line had `n>1`, so that truncation was not observed. What was lost was whole lines: the session's `samples_total` was 12 while eight lines showed `n=1`; the four others fell in windows whose `PIPE/PRESS` line is missing (79 lines for about 114 windows), and the log itself reports `LOG_LINES_DROPPED` of about 35 lines a second. `PIPE/PRESS_SAMPLE` lines go through the same log, so they can be lost the same way; the `press=` numbers and the totals on `PIPE/PRESS` show how many.

**What it cannot tell you.**
- It needs a quiet screen. Anything else that changes the picture by a big step (a notification, a video playing, an animation, loss recovery that is not flagged corrupt) can be taken for the answer to a press, which gives a false sample. Check `frame_bytes` against `quiet_bytes`.
- Presses whose answers merge into a running burst are not measured; at about two presses a second (500 ms apart) most answers fall into the previous move's burst and its 133 ms tail, so the yield drops. Compare `n` with `presses`.
- Corrupt frames are skipped, so a press answered only by a frame flagged corrupt shows up as `expired`.
- `first_us` is 1 ms coarse; a sample can show `first_us` slightly early, and a press sent in the same millisecond as the first packet can give a small negative value (counted in `order_err`).
- The press time is when the packet was handed to the network, not when the button was touched; the time from the physical press to the send is `PIPE/INPUT`.
- The constants are first guesses taken from one log; tune them from the next one.

### 9.2 `PIPE/DECHOLD`: does the hardware decoder hold pictures back?

**What it measures.** Whether feeding frame N makes the decoder hand back frame N, or an older one (N-1, N-2), and how long each picture sat inside the decoder. Today's code assumes the picture that comes out is the one that just went in; two or three held frames would be a large share of a delay of tens of milliseconds, and nothing else can see it.

**Change to what the decoder is given.** In `decode_frame_now` (`vita/src/video.c`) the access unit's presentation timestamp (`au.pts`) is now the frame's running number (the same number `PIPE/PRESS` uses; `upper` = 0, `lower` = number) instead of `0xFFFFFFFF` in both halves. It is fed so that the number can be read back. `au.dts`, the decoder init parameters and the reference-frame count are unchanged. Before each decode the output picture's `info.pts` is set to `0xFFFFFFFF`, so a decoder that does not write it cannot leave an old number behind. **Whether the Vita decoder echoes the timestamp into `info.pts` is unverified until the first hardware log.** If it does not, `rb_good` stays 0 and `rb_bad` equals the pictures handed back; the frame counts still work on their own.

**Counts.** `fed` counts decodes where `sceAvcdecDecode` returned 0 or more; `handed` is the sum of `numOfOutput`. The hold is `fed - handed`, a running value for the whole session (it does not restart each window).

**Per picture** (only when the read-back is good):
- *Lag in frame numbers* = the number just fed minus the number read back. 0 means the decoder returned the frame it was just given. The numbers are the receive thread's counter, so a frame the decode queue dropped before decoding also shows up as lag; compare with `hold`, which counts only frames the decoder actually received.
- *Hold time* = the clock read taken right after `sceAvcdecDecode` returned minus the clock read taken right before the call that fed the same-numbered frame (both reads already existed for `PIPE/DECODE`). Feed times are kept for the last `DECHOLD_FEED_RING` = 64 frame numbers; a read-back that is no longer in that ring (or was never fed) counts in `rb_stale` and gets no hold time.
- *Good read-back*: `info.pts.upper` is 0, the lower half is not 0 and not `0xFFFFFFFF`, and the number is not ahead of the frame just fed nor more than `DECHOLD_LAG_MAX` = 32 behind it. Anything else counts in `rb_bad`. A decode that returned no picture counts in neither.

**Which frame the press meter uses.** When the read-back is good, `PIPE/PRESS` takes the read-back number as the frame in `frame_texture` (section 9.1); otherwise the fed number.

**Window.** The decode thread closes its own window together with the `decode_avg_us` window (about 1 s, closed only when a picture arrives), reduces it to 32-bit values and publishes them under a sequence lock (`dechold_lock`, odd while writing). The reporter copies them with a few retries and prints the previous copy if none is consistent. The UI thread never resets a counter the decode thread writes. The window the line shows is the decode thread's last closed window, which is not aligned with the reporter's window, so a window can be printed twice or skipped now and then. Reset with the stream (`host_metrics_reset_stream`, `vita_h264_start`).

**Fields of the line.**

| Field | Meaning |
|---|---|
| `fed`, `handed` | Decodes accepted and pictures handed back in the window. |
| `hold` | `fed - handed` over the session, at window close. |
| `hold_min`, `hold_max` | Smallest and largest `hold` seen after any decode in the window. |
| `lag_min`, `lag_avg`, `lag_max` | Lag in frame numbers over good read-backs; average with two decimals; 0 when there were none. |
| `hold_us_avg`, `hold_us_max` | Hold time in microseconds over good, non-stale read-backs; 0 when there were none. |
| `rb_good`, `rb_bad`, `rb_stale` | Read-backs that passed, failed validation, and good ones whose feed time was no longer remembered. |
| `avail_min` | Smallest `sceAvcdecDecodeAvailableSize` (free room in the decoder's input buffer, bytes) read before a decode in the window; the same read the decode already made. 0 when no decode ran. |
| `pull_try`, `pull_got`, `pull_err` | Pull calls made in the window (section 5), those that returned a picture, and those that returned an error. |
| `pull_us_max` | Longest pull call, microseconds. |
| `pull_floor` | The pull floor at window close: the hold level at or below which no pull is tried. It can go down as well as up (the 3-second decay, section 5), but never below the session's starting floor (the floor the first empty pull set; not yet measured on hardware). |

Example (a decoder holding two frames): `PIPE/DECHOLD fed=60 handed=60 hold=2 hold_min=2 hold_max=2 lag_min=2 lag_avg=2.00 lag_max=2 hold_us_avg=66800 hold_us_max=71200 rb_good=60 rb_bad=0 rb_stale=0 avail_min=61440 pull_try=0 pull_got=0 pull_err=0 pull_us_max=0 pull_floor=0`

**What it cannot tell you.**
- It is only as good as the echo: with `rb_good=0` only `hold` is known, and `hold` alone cannot say which frame came out.
- Hold time is measured at the end of the decode call, so it covers time inside the decoder, not the wait before it (decode queue) or after it (waiting for the UI thread).
- A window with no picture at all is not closed (the close runs when a picture arrives), so a total stall shows the last window until output resumes.
- The line itself only observes. Since the pull (section 5) the build also acts on the hold, so `hold` is no longer the raw behaviour of the decoder: compare `pull_try` and `pull_got` with `hold` to see how much the pull changed it. `fed` and `no_output` still count only real feeds.

**Other lines added with the pull (#413).**
- `PIPE/DECMISS frame=F since_prev_us=U dur_us=D hold=H` (debug): one per normal decode that returned no picture. `since_prev_us` is the time from the start of the previous normal decode call to the start of this one (0 for the first of a session), `dur_us` this call's length, `hold` the hold after it (before any pull). It shows the call spacing below which the decoder misses. At most `DECODE_MISS_LOG_MAX` = 64 per session; the rest are counted in `miss_suppressed` on the totals line.
- `PIPE/DECPULL floor=N base=B dir=up|down frame=F` (debug): the floor changed to N; B is the session's starting floor (the floor the first empty pull set; 0 until then). `dir=up`: a pull returned no picture, so the floor rose to the hold. `dir=down`: 3 seconds passed since the last floor change, so the floor dropped one step, never below B (not yet measured on hardware). `PIPE/DECPULL error=0x... frame=F pulling off for this session` (error): a pull failed and pulling is off.
- `DECODE/ANOM buf_too_small count=N frame=F size=S avail=A` (error): the decoder's input buffer had less room than the frame, so the frame was dropped (a dropped P-frame breaks the reference chain). The first 5 per stream are printed, then suppressed.
- The `DECODE/ANOM totals` line at stream stop gains `buf_too_small`, `miss_suppressed`, `pull_try`, `pull_got`, `pull_err` (session totals) and `pull_disabled` (1 if an error turned pulling off).

### 9.3 `PIPE/RECVBUF`: how much backlog does the receive thread find?

**What it measures.** Video data that sits in the kernel's socket buffer before the receive thread reads it. All other timing starts when the receive thread reads a packet, so a standing backlog there is invisible. At 6 Mbit/s, 20 KB waiting is about 27 ms.

**What shipped.** The drain count, the bytes drained and the buffer size (this section), and the bytes waiting in the socket as `PIPE/SOCKQ` (section 9.7). The second number was first left out because `takion->sock` on Vita is a newlib file descriptor, not the SceNet socket id, and the meaning of `sceNetGetSockInfo`'s `n` and `flags` arguments and of the unit of `recv_queue_length` is not documented. Section 9.7 says how the id is now resolved (newlib's private `__vita_fd_grab`, read from the SDK's disassembly) and how the call is checked against our own socket before any sample is trusted. The unit is still undocumented: it must be settled against the `bytes` and `packets` fields of this line on hardware.

**Drained packets and bytes per wake-up.** In `takion_thread_func` (`lib/src/takion.c`) the blocking `takion_recv` wakes the thread with one packet; the drain loop then pulls up to `TAKION_RECV_DRAIN_MAX` = 256 more with zero-timeout reads. The number counted for a wake-up is how many the drain loop pulled after the waking packet (the waking packet itself is not counted), taken when the loop ends. A wake-up is one blocking receive that returned a packet. The bytes are the sum of the sizes (`drain_size` after each successful zero-timeout `takion_recv`) of exactly those packets; the waking packet is not included. The probe uses its own counters (`recvbuf_acc`); the existing `jitter_stats.drain_*` counters are left alone because the occasional "Takion jitter:" line resets them. These fields do **not** measure a backlog (see "What the first hardware log showed"): a drained count only equals "packets that were already waiting" if the zero-timeout read returns at once.

**Receive buffer size.** `rcvbuf_req` is `takion->a_rwnd` (`TAKION_A_RWND`, 512 KB on Vita) and `rcvbuf_actual` is the value read back from the kernel right after the `SO_RCVBUF` set in both connect paths (the existing `Takion SO_RCVBUF requested=... actual=...` log line is unchanged and is still printed once per connection). `rcvbuf_actual` is 0 if the read-back failed.

**Window.** The receive thread closes its own window once at least `TAKION_RECVBUF_WINDOW_MS` = 1000 have passed, judged with the millisecond clock value the loop already reads once per iteration. It reduces the counters to 32-bit values and publishes them under a sequence lock (`recvbuf_lock`, odd while writing), the same way as `PIPE/DECHOLD`. The reporter copies with a few retries and prints the previous copy if none is consistent. The window closes only when a packet arrives and a drain loop has ended, so a total stall shows the last window until packets resume. A long blocked wait is therefore counted in the window in which it ends, and that window's `wall_us` can be well over 1000 ms. The shown window is not aligned with the reporter's, so one can be printed twice or skipped now and then; two identical consecutive lines are one window. The UI thread never resets a counter the receive thread writes. State is zeroed when the receive thread starts and in `host_metrics_reset_stream`. The first window starts when the receive thread starts, not at the first packet.

**Time and traffic (added after the first hardware log).** Everything is counted by the receive thread with plain integer adds and reads of the microsecond clock (`chiaki_time_now_monotonic_us`); no allocation, lock or log call is added to the loop.

| Field | Meaning |
|---|---|
| `packets`, `bytes` | All packets and their total size received in the window: the waking ones and the drained ones. |
| `drain_empty` | Drain loops that ended because a zero-timeout read returned `CHIAKI_ERR_TIMEOUT` ("no packet"). `takion_recv` also returns that code for a transient error (ENOBUFS) on a zero-timeout call, so a few of these can be errors, not empty sockets. |
| `drain_capped` | Drain loops that ended at `drain_cap`. A drain loop that ended on any other error is in neither counter (the thread is about to stop). `drain_empty + drain_capped` is normally `wakeups`. |
| `block_us` | Time inside the blocking `takion_recv(..., UINT64_MAX)`: from the clock read just before the call to the read just after it returns. This is the thread waiting for the packet that wakes it, and nothing else. |
| `poll_us`, `poll_max_us` | Total and longest single time inside a zero-timeout `takion_recv` of the drain loop (clock read just before to just after, including the empty one that ends the loop and including the `recv()` copy of a successful one). |
| `prio`, `affinity`, `cpu` | The audio thread's own priority, affinity mask (hex) and CPU as the system reports them (`sceKernelGetThreadInfo`), read when each window is published, not per frame (0 if the call failed). Expected: `prio=64`, `affinity=0x40000` (USER_2). A different value would mean the thread is not where `audio_thread_func` put it. |
| `wall_us` | Length of the window: the microsecond clock at the close minus the clock at the previous close (the thread start for the first window). |
| `work_us` | `wall_us - block_us - poll_us`, 0 if that would be negative: packet handling, frame assembly, the decode hand-off, audio (Opus decode and the hand-off to the audio thread; since #416 not the sound output call), logging and the rest of the loop. Not measured directly. |
| `busy_pct` | `work_us / wall_us`, one decimal. |

Cost of the timing: one clock read before and one after the blocking receive (2 per wake-up) and the same pair around every zero-timeout read, so 2 per drained packet plus 2 for the call that ends the loop (none extra when the cap ends it): 4 per wake-up plus 2 per drained packet. One more read per window at the close and one at thread start. The existing millisecond read per iteration is unchanged. On Vita each read is `sceKernelGetProcessTime`. The cost of one read is now measured once per session and printed as `clock_read_ns` on `PIPE/RECVTHREAD` (section 9.8); the sections 9.6 and 9.7 probes add reads on top of these, counted in their own sections.

**Fields of the line.**

| Field | Meaning |
|---|---|
| `wakeups` | Blocking receives that returned a packet in the window. |
| `drained_avg`, `drained_max` | Average (two decimals) and largest number of packets drained after the waking packet, per wake-up. |
| `drained_bytes_avg`, `drained_bytes_max` | Bytes of the drained packets per wake-up (whole bytes): average and largest. Same packets as `drained_avg` / `drained_max`. |
| `drain_cap` | `TAKION_RECV_DRAIN_MAX`. A `drained_max` equal to it means the cap was hit in that window. |
| `rcvbuf_req`, `rcvbuf_actual` | Receive buffer size asked for and reported by the kernel, in bytes. |
| `packets`, `bytes`, `drain_empty`, `drain_capped`, `block_us`, `poll_us`, `poll_max_us`, `work_us`, `wall_us`, `busy_pct` | The time and traffic fields above, in this order. |

Example (made-up numbers): `PIPE/RECVBUF wakeups=3 drained_avg=256.00 drained_max=256 drained_bytes_avg=258293 drained_bytes_max=261090 drain_cap=256 rcvbuf_req=524288 rcvbuf_actual=524288 packets=771 bytes=775000 drain_empty=0 drain_capped=3 block_us=1200 poll_us=900000 poll_max_us=14000 work_us=98000 wall_us=1000000 busy_pct=9.8`

**What the first hardware log showed** (`26017450183_vitarps5-testing.log`, before the time fields existed).
- Established, read from the log: of 135 windows with traffic, 108 show `drained_avg=256.00` (every wake-up hit the cap), 18 mix capped and uncapped wake-ups, and 9 never reached the cap. The never-capped ones are the first seconds of a stream (for example `wakeups=78..101 drained_avg=1.96..4.35` at about 132 to 136 s). In the window at 33.4 s, `PIPE/FPS` reports `windowed_mbps=0.68` and `incoming=60`, yet the line shows `wakeups=1 drained_avg=256.00 drained_bytes_avg=114895`: 115 KB drained at one wake-up when the whole stream carries about 85 KB a second. Inside one stream (gen=2, rssi 94, steady 3.5 Mbit/s) the line changes from `wakeups=101 drained_avg=4.35` to `wakeups=3 drained_avg=256.00` between 136.4 s and 138.4 s and then stays there. Wake-ups per window (1 to 3) match packets per second divided by 257, as they would if the thread almost never left the drain loop.
- Established, read from code and disassembly: on Vita `chiaki_stop_pipe_select_single` calls `select()` with a timeval of {0,0} for a zero timeout (`lib/src/stoppipe.c:222-229`). The SDK's newlib `select()` (disassembly of `lib_a-select.o`, `libc.a`) turns the timeval into microseconds (`tv_sec * 1000000 + tv_usec`), and for every call creates a SceNet epoll (`sceNetEpollCreate`), registers each descriptor below `nfds` that is open as a SceNet socket (`__vita_fd_grab`, `sceNetEpollControl`), calls `sceNetEpollWait(epoll, events, 255, timeout_us)` with 0 for {0,0}, and destroys the epoll. So a zero-timeout "poll" is at least four SceNet kernel calls plus clearing about 8 KB of event buffer, not a flag test. The `timeout == NULL` case passes -1; the Vita-only "999999999 seconds" workaround in `stoppipe.c` wraps in the 32-bit multiply to a negative number (-1531494976), so the blocking receive also relies on `sceNetEpollWait` treating any negative timeout as infinite.
- Inference, not established: the numbers above fit a drain loop whose zero-timeout reads are not instant, so that packets keep arriving while a read is in progress and the loop rarely sees an empty socket. Why a read would take milliseconds is not known. Candidate causes: `sceNetEpollWait` with timeout 0 does not return at once in the firmware; or the receive, decode and audio threads share priority 64 (`PIPE/PRIORITY`) and the poll's kernel calls give up the CPU; or per-packet handling is slow enough that the loop really is saturated. The disassembly cannot tell these apart because `sceNetEpollWait` is a firmware call. The "saturated" explanation fits badly with 0.68 Mbit/s and a decoder idling at 1.7 ms per frame, but is not excluded.
- Confidence: high that the drained counts are not a measure of backlog; moderate that the zero-timeout read is the cause rather than a symptom; low on which mechanism. The new fields settle it: see below.

**What the second hardware log showed** (`26571013903_vitarps5-testing.log`, with the time fields). Established, read from the log (`LC_ALL=C grep -a`): `busy_pct` is already above 90 in the early windows of the stream while `drain_empty` still equals `wakeups` and `drain_capped` is 0, for example the window printed at 31918416 (`wakeups=16 drained_avg=21.75 drain_empty=16 drain_capped=0 poll_max_us=282 work_us=917147 wall_us=1000120 busy_pct=91.7`). Over the first windows it climbs from `busy_pct=50.9` (first window with traffic, 23878576) through 66.8, 72.0 and 81.8 to that 91.7. So the thread is busy before it stops finding the socket empty: the busy time is not a consequence of a standing backlog. `poll_max_us` stays under 0.5 ms in these windows. The session printed `Catchups: 0` (`VITA AUDIO :: Session stats - Frames: 9928, Catchups: 0 (0.00%)`), so the audio catch-up path never ran. Where the busy time goes is what section 9.6 measures.

**How to read it.**
- Saturated (the thread never idles, data stands in the socket): `busy_pct` high (above roughly 80), `block_us` near 0, `poll_max_us` in the tens of microseconds, `drain_capped` close to `wakeups`.
- Idle, no standing backlog: `block_us` is most of `wall_us`, `busy_pct` low, `poll_max_us` in the tens of microseconds, `drain_empty` close to `wakeups`, `drained_avg` small.
- The zero-timeout read is itself waiting: `poll_us` is a large share of `wall_us` and `poll_max_us` is in milliseconds (a true poll takes microseconds), `block_us` small, `busy_pct` low. `drain_capped` is high because the loop keeps finding the next packet. In that case the drained packet and byte counts say nothing about a backlog, and `work_us` is the honest measure of how busy the thread really is. If instead `poll_max_us` is small and `busy_pct` is low while the cap is still hit, the packets really were queued (a short-lived burst), and `drained_bytes_max` is meaningful.
- `bytes` and `packets` over `wall_us` give the real receive rate of the socket, comparable with `windowed_mbps` in `PIPE/FPS`.

**Reading drained bytes in milliseconds.** Only valid when the zero-timeout reads are shown to be instant (`poll_max_us` in tens of microseconds). Then `drained_bytes` times 8, divided by the measured bitrate, is the milliseconds of stream that were waiting at that wake-up (32400 bytes at 6 Mbit/s: 32400 x 8 / 6000000 = 43 ms). It leans high: packets that arrive while the drain loop runs are counted too, and it covers all Takion traffic on the socket (video, audio and control). A `drained_max` equal to `drain_cap` makes it a lower bound. If the reads are not instant, the figure is not a backlog: it is how much arrived while the loop was inside reads. The first hardware log is in that situation, so its byte figures (for example 258 KB per wake-up, about 590 ms of a 3.5 Mbit/s stream) must not be read as a delay.

**What it cannot tell you.**
- It counts the packets and bytes pulled after the first one, not how long they waited, and it sees only the socket buffer, not the Wi-Fi chip or the console.
- A wake-up that finds the packets one at a time says nothing about whether the socket buffer was deeper between wake-ups.
- `work_us` is a remainder: it includes anything the loop does outside the two receive calls, including the loop's own log calls, and clock-read overhead (about 4 reads per wake-up plus 2 per drained packet) is split between the three timers.
- No cost of the probe has been measured on hardware.

### 9.4 `PIPE/CONSOLE`: what the console tells us

**What it measures.** The control messages the console sends over the protobuf channel, which the stream connection mostly throws away. Two questions: what round-trip time does the console itself report (`CONNECTIONQUALITY`, field `rtt`), and which other message types arrive that we do nothing with (in particular `PERIODICTIMESTAMP`, type 27: does the PS5 send it, how often). Logging only: no message is handled differently, nothing is sent, no state outside the probe changes.

**Where each number comes from.** All of it is recorded on the Takion receive thread in `stream_connection_takion_data_idle` (`lib/src/streamconnection.c`), the handler used once the stream is running.
- `CONNECTIONQUALITY` (type 16, `ConnectionQualityPayload`): `rtt`, `target_bitrate`, `upstream_bitrate`, `upstream_loss`, `loss`. The latest value of each is kept, each only when the message carried that field (its `has_` flag). Never sent shows as `-`, not as 0. `rtt_msgs` counts the messages that carried an `rtt`.
- Ignored types: every message that reaches the switch's `default:` is counted by its type number in an array sized from the highest type in `lib/protobuf/takion.proto` (32, `CHIAKI_CONSOLE_INFO_MSG_TYPE_MAX`); a number outside it goes into `other`. The types the switch handles (`DISCONNECT`, `CONNECTIONQUALITY`, `CORRUPTFRAME`, `STREAMINFOACK`) are not counted as ignored. `PERIODICTIMESTAMP` messages are counted both as ignored and in their own `ts_*` figures.
- `PERIODICTIMESTAMP` (type 27): a count, and the time between the last two, from one read of the library's monotonic clock per such message (millisecond resolution). The raw bytes of the first one go to `PIPE/CONSOLE_TS`.

**Hand-off.** The receive thread updates a `ChiakiConsoleInfo` (`lib/include/chiaki/streamconnection.h`) inside a sequence lock (`console_info_lock`, odd while writing), so the 64-bit `rtt` and the other fields are never read half-written. The reporter (`host_metrics_report_console`, `vita/src/host_metrics.c`) copies the whole struct, retries up to 4 times, and prints the previous copy if none was consistent. Counters in the struct are session totals; the per-window figures are the growth since the reporter's previous copy. The reporter writes nothing the receive thread owns. The struct is zeroed in `chiaki_stream_connection_init` (once per session start, as the other per-run counters are) and the reporter's state in `host_metrics_reset_stream`.

**Fields of `PIPE/CONSOLE`** (printed once per window right after `PIPE/RECVBUF`).

| Field | Meaning |
|---|---|
| `quality_win`, `quality_total` | `CONNECTIONQUALITY` messages in the window and in the session. |
| `rtt_msgs_win` | Of the window's messages, how many carried an `rtt`. |
| `rtt_range_n` | How many values `rtt_min` / `rtt_max` cover: the window's, but at most the newest 16 (`CHIAKI_CONSOLE_INFO_RTT_RING`). Smaller than `rtt_msgs_win` only if more than 16 arrived in one window. |
| `rtt`, `rtt_min`, `rtt_max` | Latest `rtt` the console sent, and the smallest and largest in the window. Six decimals. `-` if none yet / none in the window. **Unit unverified** (the proto only says `double`). |
| `target_bitrate`, `upstream_bitrate`, `upstream_loss`, `loss` | Latest values the console sent, as sent; `-` if never sent. Units as in the proto; not checked against hardware. |
| `ignored_win`, `ignored_total` | Messages that reached the `default:` case in the window and in the session. |
| `types=[type:count,...]` | Session totals per ignored type number, for every type seen at least once; `other:` for a number out of range. Cut off with `...` if the text does not fit in 256 characters. `[]` if none. |
| `ts_win`, `ts_total` | `PERIODICTIMESTAMP` messages in the window and in the session. |
| `ts_gap_ms` | Milliseconds between the last two `PERIODICTIMESTAMP` messages; `-` before the second one. |

Example: `PIPE/CONSOLE quality_win=1 quality_total=84 rtt_msgs_win=1 rtt_range_n=1 rtt=0.018250 rtt_min=0.018250 rtt_max=0.018250 target_bitrate=6000 upstream_bitrate=0 upstream_loss=0.0000 loss=0 ignored_win=3 ignored_total=251 types=[27:84,3:167] ts_win=1 ts_total=84 ts_gap_ms=1002` (all numbers made up).

**`PIPE/CONSOLE_TS`.** Printed once per session, from the UI thread, the first window after the first `PERIODICTIMESTAMP` message was seen: `PIPE/CONSOLE_TS first len=<n> hex=<bytes>`. `len` is the true length of that whole protobuf message; `hex` is its first 64 bytes (`CHIAKI_CONSOLE_INFO_FIRST_TS_CAP`), and ` truncated_to=64` is appended if the message was longer. It is the raw message including the type field, not decoded: `periodic_ts_info` is a callback-typed bytes field in nanopb and the decoding is left untouched. Example (made up): `PIPE/CONSOLE_TS first len=12 hex=081bda01080a0400000000`.

**Handlers before the stream runs.** The expect-bang and expect-streaminfo handlers do not drop other types silently: a message of the wrong type is logged at error level (`expected bang payload but received something else: <type>` and the streaminfo equivalent) and returned from, apart from `DISCONNECT`, which is handled. They are not instrumented, because a periodic timestamp arriving there would already be logged.

**What it cannot tell you.**
- `rtt` is the console's estimate, not a measurement of ours, and its unit is unverified until the first hardware log. Do not convert it before then.
- A type in the `types` list only means we do nothing with it; it says nothing about what the message contains.
- A message that fails to decode is logged as an error by the existing code and not counted here.
- The lines print only with `show_latency` on, like the other probes. Window figures are not aligned with the console's cadence, so a message can appear in a neighbouring window.
- No cost of the probe has been measured on hardware; per message it adds a few integer updates and, for a periodic timestamp, one clock read and one copy of at most 64 bytes (once).

### 9.5 `PIPE/SPS`: what the stream says about its own reordering and buffering

**What it shows and why.** The first hardware log has the hardware decoder holding a constant 8 pictures in one session and 4 in the next (section 9.2), with the same `max_num_ref_frames=9` in the SPS of both. Our own SPS parser (`lib/src/bitstream.c`, `header_h264`) stops at `gaps_in_frame_num_value_allowed_flag`; the fields that say how many pictures a decoder may hold before it outputs one come after that. `PIPE/SPS` prints the whole SPS of each session once, so the two sessions can be compared field by field. A second line, `PIPE/SPS_REPEAT`, counts SPS that arrive again later in the same session and differ from the first. It reports what the stream declares. It does not report what the Vita decoder does with it.

**Where the bytes are taken.** The stream header (SPS, then PPS) reaches the Vita app unmodified: `lib/src/videoreceiver.c` calls the video callback with `profile->header`, it arrives in `host_video_cb` (`vita/src/host_callbacks.c`) and goes through `vita_h264_decode_frame()` (`vita/src/video.c`) like any frame. The header seen in log 26017450183 starts with a 4-byte start code and the SPS NAL directly (`00 00 00 01 67 4d 40 20 ...`), with no access unit delimiter in front, followed by a 4-byte start code and the PPS. `vita_h264_decode_frame()` calls `sps_probe_observe()` (`vita/src/sps_probe.c`) with the same pointer and length it then copies into the decode queue. The probe only reads: the bytes handed to the decoder, their order, the queue and its timing are unchanged.

**Which thread does what.**
- Receive thread (in `sps_probe_observe`): per buffer, a few byte compares to see whether it starts with a 3- or 4-byte start code followed by a NAL header of type 7 (SPS). Only for such a buffer: find the end of the NAL (next `00 00 00` / `00 00 01`, the end of the buffer, or `SPS_PROBE_SCAN_MAX` = 512 bytes), and either copy at most `SPS_PROBE_CAP` = 128 bytes of it into a fixed buffer (the first SPS of the session; the true length is kept) or compare it with that copy (length first, then the bytes up to the cap) and bump a counter. No parsing, allocation, formatting or logging happens there. The record is published under a sequence lock (odd while writing).
- UI thread (`host_metrics_report_sps`, called from `host_metrics_update_latency`, `vita/src/host_metrics.c`): a plain read of the lock word each tick; only when it moved, a consistent copy (up to 4 tries; if every try overlapped a write it looks again on the next tick). The first SPS is read by `sps_probe_parse()` (`vita/src/sps_probe.c`, standard C only, no allocation, a stack buffer of at most 128 bytes) and printed once. The bytes come from the network, so the reader is our own and bounds-checked; the bundled h264-bitstream library (`vita/third_party/h264-bitstream`) is not used on this path (see "How the SPS is read").
- Reset: `sps_probe_reset()` in `vita_h264_start()` and the reporter's state in `host_metrics_reset_stream()`, so a second session in the same app run prints its own `PIPE/SPS`.

**`PIPE/SPS` (once per session, whatever `show_latency` says).**

| Field | Meaning |
|---|---|
| `sps_len` | True length in bytes of the SPS NAL unit (NAL header byte included, start code not). |
| `profile_idc`, `level_idc` | As in the SPS (77 = Main; 32 = level 3.2). |
| `constraint_flags` | The raw byte after `profile_idc`, in hex (constraint_set flags and the two reserved bits). |
| `poc_type` | `pic_order_cnt_type`: 0, 1 or 2. 2 means output order equals decode order. |
| `frame_mbs_only` | `frame_mbs_only_flag`. |
| `max_num_ref_frames` | `max_num_ref_frames` of the SPS. |
| `vui` | 1 if the SPS carries VUI parameters, else 0. |
| `bitstream_restriction` | `bitstream_restriction_flag`; `-` if there is no VUI (the field does not exist then). |
| `num_reorder_frames` | `max_num_reorder_frames` of the standard; `-` unless `bitstream_restriction` is 1. |
| `max_dec_frame_buffering` | As in the standard; `-` unless `bitstream_restriction` is 1. |
| `hex_cap`, `hex` | The stored SPS bytes in hex, at most `hex_cap` = 128 bytes. If the SPS was longer, ` truncated_to=<n>` follows. |

A value the stream does not contain prints as `-`, never as 0. Example (the header bytes dumped in log 26017450183, parsed natively by `sps_probe_parse()`; not yet seen on hardware): `PIPE/SPS sps_len=28 profile_idc=77 constraint_flags=0x40 level_idc=32 poc_type=2 frame_mbs_only=1 max_num_ref_frames=9 vui=1 bitstream_restriction=1 num_reorder_frames=0 max_dec_frame_buffering=9 hex_cap=128 hex=674d4020918a03c045fbc05a808080a00000fa400075301134387454`.

**How the SPS is read (`sps_probe_parse`).** A bit reader over the stored bytes: every read is checked against the length, so running out of bits is a refusal (`fail=truncated`), never a read past the end and never zeros printed as real values (once a read has failed, the first error is kept and nothing is printed from the partial result). The NAL unit is first copied into a fixed 128-byte buffer with its emulation-prevention bytes (`00 00 03`) removed; the copy never exceeds the stored length. The reader walks the fields in order up to and including the VUI bitstream restriction (profile, level, id, the high-profile chroma, bit-depth and scaling-list fields, frame number and picture order count, reference frames, size, cropping, VUI with aspect ratio, overscan, video signal, chroma location, timing and both HRD blocks). Every value that sizes a loop or selects a table is checked against its limit before it is used:

| Value | Limit | Refusal |
|---|---|---|
| `seq_parameter_set_id` | 0 to 31 | `sps_id_out_of_range` |
| `chroma_format_idc` | 0 to 3 (3 means 12 scaling lists, else 8) | `chroma_format_out_of_range` |
| `pic_order_cnt_type` | 0 to 2 | `poc_type_out_of_range` |
| `num_ref_frames_in_pic_order_cnt_cycle` | 0 to 255 | `poc_cycle_too_large` |
| HRD `cpb_cnt_minus1` (NAL and VCL) | 0 to 31 | `cpb_cnt_too_large` |
| Exp-Golomb code | fewer than 32 leading zeros | `ue_too_long` |

Scaling lists are walked (their size is fixed at 16 or 64 entries and the loop ends early when the running scale reaches 0) but not stored, so no table is indexed by a stream value. The high-profile fields are read for the profile numbers the standard lists (100, 110, 122, 244, 44, 83, 86, 118, 128, 138, 139, 134, 135).

**`PIPE/SPS` when the SPS cannot be read.** `PIPE/SPS fail=<r> sps_len=<n> hex_cap=128 hex=<bytes>` (plus ` truncated_to=<n>` if cut), so the line can be decoded by hand. Reasons: `longer_than_cap` (the SPS is longer than 128 bytes, so only part is stored and it is not read), `not_an_sps` (the first byte is not an SPS NAL header), `truncated` (ran out of bits before the last field read), and the six range reasons in the table above. Example: `PIPE/SPS fail=truncated sps_len=5 hex_cap=128 hex=674d4020ff`.

**`PIPE/SPS_REPEAT`.** Printed from the UI thread only when a count changed since the last print, and at most once per second: `PIPE/SPS_REPEAT seen_again=<a> differed=<d>`. `seen_again` is how many buffers beginning with an SPS were seen after the first one in this session; `differed` is how many of those were not identical to the first (length, then bytes up to the 128-byte cap). Both are session totals. A differing SPS is counted, not parsed or logged in full. Example: `PIPE/SPS_REPEAT seen_again=3 differed=0` (made up).

**What it cannot tell you.**
- It reports what the stream declares, not what the Vita decoder does with it. The decoder is created with its own parameters (`REF_FRAMES`, section 5) and may hold pictures for reasons not in the SPS; compare with `PIPE/DECHOLD` (section 9.2).
- Only an SPS at the very start of a buffer is noticed: the stream header, and in-band SPS only if they come first in a frame buffer. An SPS behind another NAL (an access unit delimiter, an SEI, a PPS) is not seen, so `seen_again=0` does not prove the console sent none.
- A later SPS that differs is only counted. Its fields are not read, so a changed `max_dec_frame_buffering` mid-session would show up as `differed>0` without saying what changed.
- An SPS whose end is not found within 512 bytes is taken to end there.
- Fields after the bitstream restriction (the trailing bits) are not read or checked, and values that only describe the picture (width, height, cropping, bit depth) are skipped, not range-checked: they size nothing.
- The numbers come from one parse of one SPS; no cost has been measured on hardware beyond "a few byte compares per buffer".

### 9.6 `PIPE/RECVTIME`: where does the receive thread's time go?

**What it measures.** `PIPE/RECVBUF` (9.3) says how long the receive thread is busy (`work_us`) but not on what. This line splits `work_us` of the same window by what the thread was doing: handling video packets, audio packets or control packets, and inside those, two suspects: the video hand-off to the decoder queue and the audio callback (since #416 the hand-off to the audio thread; the call that plays audio, `sceAudioOutOutput`, moved to its own thread and is on `PIPE/AUDIOOUT`, 9.9). It also counts how much of the time went into log calls. Logging only: no behaviour changes.

**Same window.** It is accumulated and published by the same window close, under the same sequence lock, as `PIPE/RECVBUF` (9.3), and printed right after it under `show_latency`. The accumulators are zeroed with the 9.3 ones. Nothing here is a second window.

**Who writes what.** Only the receive thread. The Takion loop (`takion_thread_func`, `lib/src/takion.c`) writes the packet-class buckets. `vita_audio_cb` (`vita/src/audio.c`), `host_video_cb` (`vita/src/host_callbacks.c`) and the log paths write their own fields; they run synchronously on the receive thread (the audio callback via `takion_handle_packet_av` -> `stream_connection_takion_av` -> `chiaki_audio_receiver_av_packet` -> `chiaki_opus_decoder_frame`; the video callback from `chiaki_video_receiver_av_packet` / `chiaki_video_receiver_flush_frame`). Each of them first compares the calling thread's id with the one the receive thread recorded at start (`recvtime_thread_id`), and writes nothing from any other thread. There is no lock, no allocation and no log call on these paths.

**How a packet's handling time is measured.** A packet's handling time is the span from the clock read that ended its receive (or the end of its socket-queue query, 9.7) to the next clock read the loop makes anyway: the start of the next zero-timeout receive. That reuses the reads 9.3 already makes, so it adds none per packet. The one exception: when a drain loop ends at the cap there is no following poll, so one extra read closes the last packet (at most one per capped wake-up). The class comes from the Takion base type of the packet's first byte, as `takion_handle_packet` dispatches it: video, audio (haptics packets share the audio base type, so they are counted as audio), control. Anything else, and packets handled from the postponed-packet flush, are not in a class and fall into `unacct_us`.

**Fields.** All per window, times in microseconds saturated at 32 bits.

| Field | Meaning |
|---|---|
| `video_n`, `video_us`, `video_max_us` | Packets of the video class, total time in `takion_handle_packet` for them, longest single one. |
| `audio_n`, `audio_us`, `audio_max_us` | Same for audio (and haptics). |
| `ctrl_n`, `ctrl_us`, `ctrl_max_us` | Same for control. |
| `vsubmit_n`, `vsubmit_us`, `vsubmit_max_us` | Subset of `video_us`: calls of `host_video_cb` (the whole callback, including its call of `vita_h264_decode_frame` and any wait for a free slot in the decode queue). |
| `acb_n`, `acb_us`, `acb_max_us` | Subset of `audio_us`: calls of `vita_audio_cb`, which since #416 is the hand-off: the mutex, the copy into the queue, the catch-up check and the probe bookkeeping. It is timed from the start of the callback to its return. The Opus decode before it is in `audio_us` but not in `acb_us`. |
| `acatchup` | Pushes on which the catch-up rule dropped frames (section 6); the same count is printed as `catchups` on `PIPE/AUDIO`. |
| `work_us` | The `work_us` of the `PIPE/RECVBUF` line of the same window, repeated. |
| `unacct_us` | `work_us - video_us - audio_us - ctrl_us`, printed **signed**. Only the three classes are subtracted: `vsubmit`, `acb` and the log fields are already inside a class and must not be subtracted again. A negative value is printed as is (never clamped to 0). It contains everything the loop does outside packet handling, the postponed-packet flush, the time of the socket-queue queries (9.7, printed on their own line) and any packet type outside the three classes. |
| `log_n`, `log_us`, `log_max_us` | Log calls made by the receive thread that were actually written (passed the level mask and `vita_log_should_write_level`), their total time and the longest. |
| `vlog_us`, `alog_us`, `clog_us` | `log_us` split by the class of the packet being handled when the call was made. What is left of `log_us` was logged outside packet handling. |
| `log_block` | Written log calls of a level other than DEBUG: those take the blocking mutex path in `vita_log_submit_line` (`vita/src/logging.c`). |

**The log fields are not a class.** `log_us` is a subset that cuts across `video_us`, `audio_us`, `ctrl_us` and `unacct_us`. It is never subtracted in the `unacct_us` formula. The timed span of a lib log call (`CHIAKI_LOG*`) is the whole Vita callback `log_cb_debugnet` (`vita/src/context.c`): the second formatting, `sceClibPrintf`, `vita_log_submit_line`. The `vsnprintf` the lib does before it calls the callback (`chiaki_log` in `lib/src/log.c`) is **not** covered. For the Vita `LOGD/LOGW/LOGE` macros (`vita/include/context.h`) the span runs from the timestamp read they already make to after `vita_log_submit_line` returns.

**Cost of the probe (added clock reads).**
- Takion loop: none per packet. One per capped wake-up. One per socket-queue sample (9.7).
- `vita_audio_cb`: 2 reads per frame on the receive thread (start, end); the start read also serves the queue occupancy window.
- `host_video_cb`: 2 per submitted frame.
- A lib log call: 2 on the receive thread (start and end of `log_cb_debugnet`), none on other threads. A Vita-macro log call: 1 on the receive thread (the start is the timestamp it reads anyway), none on other threads.
- The "am I the receive thread" check is one `sceKernelGetThreadId()` call per audio frame, video frame and log call, from any thread, with no clock read. Its cost is measured once per session as `thread_id_ns`, and the clock read as `clock_read_ns` (both on `PIPE/RECVTHREAD`, 9.8); multiply by the call counts to get the probe's own cost. Neither value is known before the first hardware log.

Example (made-up numbers, not from hardware; field order is the format string in `vita/src/recv_probe.c`): `PIPE/RECVTIME video_n=420 video_us=210000 video_max_us=9000 audio_n=100 audio_us=60000 audio_max_us=900 ctrl_n=30 ctrl_us=2000 ctrl_max_us=300 vsubmit_n=55 vsubmit_us=150000 vsubmit_max_us=8000 acb_n=100 acb_us=300 acb_max_us=40 acatchup=0 work_us=300000 unacct_us=28000 log_n=300 log_us=40000 log_max_us=900 vlog_us=25000 alog_us=0 clog_us=3000 log_block=2`

**How to read it.**
- Audio: what is expected after #416 (not measured yet) is `acb_us` and `acb_max_us` small, microseconds per frame, because the callback no longer waits on the sound hardware; the milliseconds that `aout_us` showed on the #413 probes build now belong to `PIPE/AUDIOOUT` (9.9). `audio_us - acb_us` is Opus decode, decryption and the audio receiver. A large `acb_max_us` would mean the mutex was contended or the thread was descheduled inside the callback. `aout_*`, `ashort` and `askip` were removed from this line in #416.
- Video submit is where it waits: `vsubmit_us` is most of `video_us`, with `vsubmit_max_us` near 10 ms (the decode queue's bounded wait in `vita_h264_decode_frame`, `vita/src/video.c`).
- Logging: `log_us` large compared with `work_us`, mostly in `vlog_us` (the lib's per-frame lines).
- Nothing accounts for it: `unacct_us` is most of `work_us` and the class buckets are small. Then the time is outside packet handling (the loop's own work, the postponed flush) or the thread is not running (preempted by another thread of equal or higher priority); `PIPE/RECVTHREAD` (9.8) shows priority and core.
- A clearly negative `unacct_us` means the class buckets add up to more than the window's remainder: the clock reads disagree (see `clock_read_ns`) or `work_us` was clamped.

**What it cannot tell you.**
- It measures elapsed time, not CPU time: a thread that is preempted while inside `takion_handle_packet` is charged for the wait too. It cannot tell waiting on a lock or the sound hardware from being descheduled.
- The class split sees time inside `takion_handle_packet` only; the sub-buckets cover three call sites, not the whole of the handling.
- All of it is "to be measured": no result from hardware is recorded here yet.

### 9.7 `PIPE/SOCKQ`: bytes waiting in the socket

**What it measures.** How much `sceNetGetSockInfo` says is queued on the Takion socket (`recv_queue_length`), sampled by the receive thread. Unit: the raw `recv_queue_length` value; the unit is not documented, to be settled against `PIPE/RECVBUF` bytes on hardware.

**From the newlib descriptor to the SceNet id.** `takion->sock` is a newlib descriptor. Evidence (disassembly of the SDK's `libc.a`, `arm-vita-eabi-objdump`): `recvfrom` calls `__vita_fd_grab(fd)`, loads `[r0, #0]` of the returned pointer as the first argument of `sceNetRecvfrom`, then calls `__vita_fd_drop(ptr)`; `getsockname` does the same with `sceNetGetsockname`; `socket` stores the `sceNetSocket` result at `[entry, #0]` and the byte `2` at `[entry, #4]`; `__vita_fd_grab` returns `__vita_fdmap[fd]` after incrementing the reference count at `[entry, #8]` (NULL for a descriptor outside 1..255 or unset), and `__vita_fd_drop` decrements it (and would close the socket at a count of 1, which cannot happen while the grab holds one). So the id is the leading `int`, the kind byte is `2` for a socket. `takion_recvprobe_setup` (`lib/src/takion.c`) declares the two private functions itself, grabs once, reads the id, checks the kind byte, and drops.

**Self-check, once per receive-thread run, before the loop.** It calls `sceNetGetSockInfo(id, &info, 1, flags)` with room for exactly one entry (the SDK headers do not say what `n` means; one entry is an assumption) and compares: the returned `s` field with the id, and the returned `local_port` with the port `getsockname` reports for the descriptor (accepted if equal to it either as stored or after `ntohs`, because the byte order of `local_port` is not documented). The last argument is undocumented too. `SCE_NET_SOCKINFO_F_SELF` comes from the header's enum "flags for ::SceNetSockInfo structure" (which also holds wait-state bits), so it may describe the struct's own `flags` field and the argument may be a reserved 0. The check therefore tries `flags = 0` (`TAKION_SOCKQ_INFO_FLAGS_NONE`) first and, only if that does not pass, `SCE_NET_SOCKINFO_F_SELF` (`TAKION_SOCKQ_INFO_FLAGS_SELF`). The value that passed is used for every sample and printed as `sockq_flags`. If neither passes, `ok=0` and no sample is taken for the session. Both return codes and the raw values of the last attempt are kept for `PIPE/RECVTHREAD` (9.8). No queue length is ever printed unless it was measured.

**When it samples.** Once per wake-up, right after the blocking receive returns and before that packet is handled; and after every 64th drained packet inside a drain loop (`TAKION_SOCKQ_DRAIN_SAMPLE_EVERY`), so a thread that wakes only 1 to 3 times a second still gives samples. Each query is timed from the clock read the loop already made when the receive returned to one read after the call: 1 added clock read per sample. The query time is not inside any packet class (the packet's handling is timed from the end of the query) and so lands in `unacct_us`.

**Fields of the line.** `PIPE/SOCKQ ok= n= min= avg= max= wake_avg= wake_max= query_us= query_max_us= err=`

| Field | Meaning |
|---|---|
| `ok` | 1 if the self-check passed and sampling is on. |
| `n`, `min`, `avg`, `max` | Number of samples in the window and the smallest, integer average and largest `recv_queue_length` over all of them (0 when `n` is 0). |
| `wake_avg`, `wake_max` | Average and largest over only the samples taken right after a blocking receive returned. |
| `query_us`, `query_max_us` | Total and longest time spent inside the queries of the window. |
| `err` | Queries that failed (or returned a negative length) in the window; not in the samples. |

Example (made-up numbers): `PIPE/SOCKQ ok=1 n=14 min=0 avg=21000 max=96000 wake_avg=18000 wake_max=33000 query_us=900 query_max_us=120 err=0`

**How to read it.** Compare `avg`/`max` with `bytes` and `packets` of `PIPE/RECVBUF` to settle the unit. If the unit is bytes, `max` times 8 divided by the bitrate is the milliseconds of stream waiting at that sample (9.3's byte-to-milliseconds reading, but from the system's own queue count rather than from the drain loop). `wake_*` is what was already queued when the thread came back from waiting; if `wake_avg` is large while `PIPE/RECVTIME` shows the thread blocked in nothing, data really stands in the socket.

**What it cannot tell you.** It is a point sample, not a continuous measurement: up to 64 drained packets pass between two drain samples. It sees the socket only, not the Wi-Fi chip. The queue length is not necessarily the whole backlog if the firmware holds more elsewhere. The unit, the meaning of `n` and `flags`, and whether the call has a side effect on the socket are not documented: all to be measured.

### 9.8 `PIPE/RECVTHREAD`: which core and priority does the receive thread really have?

**What it measures.** The receive thread's priority, affinity mask and CPU as the system reports them (`sceKernelGetThreadInfo` for the thread's own id), not as our constants say. The thread starts at priority `TAKION_RECV_THREAD_PRIORITY` on `SCE_KERNEL_CPU_MASK_USER_0` and, since #416, nothing moves it: `vita_audio_cb` only queues the frame, and the sound output runs on the VitaAudio thread (section 6). So the expected reading is current values equal to the `start_*` values (USER_0, priority 64) for the whole stream. Before #416 the first audio frame re-pinned this thread to USER_2; hardware logs of the #413 probes build showed that move (`PIPE/RECVTHREAD` confirmed the thread went from core 0 to core 2 about a second after audio started).

**When it is sampled and printed.** The receive thread samples at each window close, off the per-packet path, and once at thread start. The start sample is kept in the once-per-session facts and printed on every line as `start_*`, because the reporter only sees whichever window is published when it runs (once a window, only while the latency printing is on) and may never see the start window itself. The reporter prints the line at the first window it sees and again whenever the current priority, affinity mask or CPU differs from what it printed last; that state is reset in `host_metrics_reset_stream`. One line therefore shows "started on X, now on Y".

**Fields.** `PIPE/RECVTHREAD prio= affinity=0x cpu= last_cpu= info_rc= start_prio= start_affinity=0x start_cpu= start_info_rc= audio_started= clock_read_ns= thread_id_ns= sockq_ok= sockq_flags= sockq_id= sockq_info_rc= sockq_info_rc_self= sockq_info_id= sockq_info_port_raw= sockname_rc= sockname_port_net= sockname_port_host=`

| Field | Meaning |
|---|---|
| `prio`, `affinity`, `cpu`, `last_cpu` | `currentPriority`, `currentCpuAffinityMask` (hex), `currentCpuId`, `lastExecutedCpuId` from `SceKernelThreadInfo`. |
| `info_rc` | Return code of `sceKernelGetThreadInfo` (0 is success; the other fields are 0 otherwise). |
| `start_prio`, `start_affinity`, `start_cpu`, `start_info_rc` | The same sample taken once when the receive thread started, before its loop. |
| `audio_started` | 1 once `vita_audio_cb`'s one-time init has succeeded (`vita_audio_started()`): queue, audio thread and output config in place. It no longer says anything about this thread's core. |
| `clock_read_ns` | Cost of one `chiaki_time_now_monotonic_us()` read, from 1000 back-to-back reads timed once at receive-thread start (`TAKION_PROBE_CLOCK_READS`), in nanoseconds. Its resolution is 1 ns only because of the averaging over 1000 reads. |
| `thread_id_ns` | Cost of one `sceKernelGetThreadId()` call, timed the same way (1000 back-to-back calls at receive-thread start), in nanoseconds. This is the "am I the receive thread" check made by every log call, audio frame and video frame (9.6). 0 off Vita. |
| `sockq_ok`, `sockq_flags`, `sockq_id`, `sockq_info_rc`, `sockq_info_rc_self`, `sockq_info_id` | The 9.7 self-check: whether it passed, the last argument that passed (-1 if none), the SceNet id resolved (-1 if not), the return codes of the `flags = 0` attempt and of the `SCE_NET_SOCKINFO_F_SELF` attempt (-2147483648 means that attempt was not made because the first passed), and the `s` field of the last attempt. |
| `sockq_info_port_raw`, `sockname_rc`, `sockname_port_net`, `sockname_port_host` | The `local_port` field `sceNetGetSockInfo` returned (unconverted), the return code of `getsockname`, and its port as stored and after `ntohs`. |

Example (made-up numbers): `PIPE/RECVTHREAD prio=64 affinity=0x10000 cpu=0 last_cpu=0 info_rc=0 start_prio=64 start_affinity=0x10000 start_cpu=0 start_info_rc=0 audio_started=1 clock_read_ns=450 thread_id_ns=300 sockq_ok=1 sockq_flags=0 sockq_id=7 sockq_info_rc=0 sockq_info_rc_self=-2147483648 sockq_info_id=7 sockq_info_port_raw=51234 sockname_rc=0 sockname_port_net=51234 sockname_port_host=51234`

**How to read it.** `affinity` equal to `start_affinity` (`0x10000`, USER_0) with `prio=64` and `cpu=0` means the thread was not moved (expected after #416, not measured yet). The reporter prints this line at the first window it sees and again when `prio`, `affinity`, `cpu` or `audio_started` changed. With no move it therefore normally prints twice: a first line usually with `audio_started=0` (the first window comes before the first audio frame), and a second line with `audio_started=1` and an unchanged `affinity=0x10000`. That second line is the confirmation that audio has started and the thread is still on USER_0; a line with a different `affinity` or `cpu` means something moved the thread. The recv, decode and audio threads are each pinned to their own core, so equal priority (all 64) does not make them time-slice against each other; if the recv thread did share a core with another busy thread, `PIPE/RECVTIME` would show a large `unacct_us` or inflated class times. `clock_read_ns` tells how much of `PIPE/RECVBUF`'s `work_us` can be clock overhead (4 reads per wake-up plus 2 per drained packet).

**What it cannot tell you.** It is a sample once a window, so a core change inside a window shows at the next close. It says where the thread is, not whether it was waiting. Values are "to be measured"; no hardware result is recorded here yet.

### 9.9 `PIPE/AUDIO` and `PIPE/AUDIOOUT`: is audio delivered and played without gaps?

**What it measures.** Why audio might crackle, which no other line shows. Two lines, written by two threads (#416):
- `PIPE/AUDIO` is the receive side: how many audio packets and frames arrive, how many are new, how many frame indexes go missing, what reaches `vita_audio_cb`, how full the hand-off queue is and whether the catch-up rule dropped frames.
- `PIPE/AUDIOOUT` is the output side: what the VitaAudio thread did with the sound hardware, and whether its calls were late.

Logging only. Both are printed once per reporter pass right after `PIPE/RECVTIME`, in the order `PIPE/RECVTIME`, `PIPE/AUDIO`, `PIPE/AUDIOOUT`, `PIPE/SOCKQ`. Before #416 the output fields were on `PIPE/AUDIO`; they are now on `PIPE/AUDIOOUT` and `out_forced` is gone with the old output gate.

**Where each count accumulates.**
- `PIPE/AUDIO`: all on the receive thread, in `recvtime_acc.audio_stats`, reset and published by the same window close as the rest (same window as `PIPE/RECVBUF`, 9.3). The lib audio receiver (`lib/src/audioreceiver.c`) writes the receiver counters: it reaches the accumulator through its session (`session->stream_connection.takion.recvtime_acc`). `vita_audio_cb` (`vita/src/audio.c`) writes the rest (`decoded`, `catchup_frames`, the `q_*` samples) and `acatchup`. The audio receiver code is shared with haptics (one receiver instance each, same functions); haptics are kept out of every audio count (`haptic_pkts` is the only haptics figure).
- `PIPE/AUDIOOUT`: all on the VitaAudio thread, in private counters (`AudioOutAcc`, `vita/src/audio.c`), which it alone touches.

**`PIPE/AUDIO` fields.** `PIPE/AUDIO net_pkts= haptic_pkts= frames_new= frames_dup= frames_missing= gap_events= concealed= decoded= catchups= catchup_frames= q_min= q_avg= q_max=`

| Field | Meaning |
|---|---|
| `net_pkts`, `haptic_pkts` | AV packets that reached `chiaki_audio_receiver_av_packet`, audio and haptics, counted at entry before any validity check. |
| `frames_new` | Audio frames the receiver accepted (the `chiaki_seq_num_16_gt` branch of `chiaki_audio_receiver_frame`); each is passed to the sink. |
| `frames_dup` | Units the receiver discarded because their frame index is not newer than the last accepted one. Each packet carries redundant copies of earlier frames, so this is normally large (about as many as `frames_new` times the redundancy). Units skipped at start-up (before the 16-bit index could have wrapped) never reach the check and are not counted. |
| `frames_missing`, `gap_events` | Frame indexes skipped between two consecutive accepted frames: the jump minus one (`chiaki_takion_probe_seq16_missing`), and the number of jumps. The jump is the 16-bit modular difference, so the wrap from 0xffff to 0 is not a gap. The first accepted frame of a receiver has no baseline and is not counted. A frame that arrives late after its successor was accepted is discarded as a duplicate, so it stays counted as missing. The gap is what drives concealment, so it is computed in every build. |
| `concealed` | "Lost frame" calls handed to the audio sink (section 6, #440): `min(missing, 5)` per jump, so about `frames_missing` except on jumps above the cap. Never counts haptics. |
| `decoded` | Frames that reached `vita_audio_cb` (after opus decoding), concealed frames included. `frames_new + concealed - decoded` is frames lost between the receiver and the callback, mostly opus decode failures. `decode_err` is not printed: the opus decoder (`opusdecoder.c`) has no path to the accumulator without restructuring, so failures are only derivable that way. |
| `catchups`, `catchup_frames` | Pushes on which the catch-up rule (section 6) dropped frames, and the total number of queued frames it dropped. Normally 0 and 0. The same event is logged as `VITA AUDIO :: audio catchup: dropped N frames, M queued` and counted in the end-of-session `Catchups` line. |
| `q_min`, `q_avg`, `q_max` | Hand-off queue occupancy in frames, one sample per push, taken after the push and after any catch-up (so a catch-up shows as a sample of 2, the kept device buffer). `q_avg` has two decimals. `q_min` prints 0 when the window had no sample. The samples come from the receive thread, so they are never taken while the queue is only being drained: a stall in the stream gives no samples, not low ones. (`PIPE/LATENCY` prints the same samples as `audio_q_avg` and `audio_q_max` on its own 1 s window.) |

**`PIPE/AUDIOOUT` fields.** `PIPE/AUDIOOUT win= out_calls= out_frames= aout_us= aout_max_us= rest_n= rest_err= rest_min= rest_max= out_dry= out_gap_max_us= out_late= waits= wall_us= prio= affinity=0x cpu=`

| Field | Meaning |
|---|---|
| `win` | Number of windows the audio thread has published this session (0 before the first). It is part of the same consistent copy as the other fields. A `win` that repeats between two lines means the line is a repeat of the last window: the audio thread published nothing new (it was not outputting). |
| `out_calls`, `out_frames` | Calls to `sceAudioOutOutput` in the window and the frames they handed over (`out_calls` times `device_buffer_frames`). |
| `aout_us`, `aout_max_us` | Total and longest single time inside `sceAudioOutOutput` (32-bit, saturating). This is the time the receive thread used to spend on the call before #416 (roughly 70 to 85 percent of its elapsed time on the #413 probes build, measured as `aout_us` on `PIPE/RECVTIME`). The call blocks until the hardware can take the buffer, so a call is expected to last about one device buffer's play time (20 ms for 2 frames of 480 samples at 48 kHz) when the thread keeps up. |
| `rest_n`, `rest_err` | Reads of `sceAudioOutGetRestSample` (one before each output call, statistic only) that returned a value >= 0 and < 0. |
| `rest_min`, `rest_max` | Smallest and largest of the non-negative values (0 when `rest_n` is 0). The header documents the call only as "number of remaining samples to be output on the specified port, < 0 on error". |
| `out_dry` | Output calls whose preceding read gave a value <= 0 (an error return counts too). Raw value: what a rest of zero means for what is heard is **not established**. |
| `out_gap_max_us`, `out_late` | Longest time from one `sceAudioOutOutput` returning to the next being called, and the number of such gaps longer than the play time of one device buffer (`device_buffer_samples * 1000000 / rate` microseconds, derived at run time). The gap includes the time the thread slept waiting for a device buffer's worth of frames (`waits`). The first call of the session has no previous call and is not counted. |
| `waits` | Times the thread went to sleep because less than one device buffer was queued. |
| `wall_us` | Length of the window: from the previous window's close (for the first window, the start of its first output call) to the return of the call that closed this one. |

**The `PIPE/AUDIOOUT` window.** It is the audio thread's own, not the receive thread's. It closes inside the audio thread, right after an output call returns, once at least 1 s (`AUDIO_OUT_WINDOW_US`) has passed since the window started; the thread then publishes the counters under a sequence lock (`audioout_lock`, odd while writing, `audioout_pub`, both in `context.stream`) and zeroes its counters. Because it closes only after an output call, a thread that is starved (asleep waiting for frames, or stuck in the call) shows its last window again until sound resumes: a repeated `PIPE/AUDIOOUT` line is a sign of that, not of a quiet window, and it is recognised by an unchanged `win`. It is not aligned with the reporter's window or with the receive thread's, so the same window can be printed twice, or one skipped, between two `PIPE/AUDIO` lines; compare figures per second (`wall_us`), not by line. The reporter (`host_metrics_update_latency`, `vita/src/host_metrics.c`) copies the published window the same way as `PIPE/DECHOLD` (up to `AUDIOOUT_READ_ATTEMPTS` = 4 tries at a consistent copy) and prints the last consistent copy if none succeeds. The line is all zeros until the first window closes (about the first second after audio starts) and for the whole session if audio is off. The published window, `win` included, is zeroed with the stream (`host_metrics_reset_stream`, at stream start and after every quit, when no audio thread is alive), so a window never carries over from an earlier session and `win` counts from 0 each session.

Examples (made-up numbers, not from hardware; field order is the format strings in `vita/src/recv_probe.c`):

`PIPE/AUDIO net_pkts=100 haptic_pkts=0 frames_new=100 frames_dup=300 frames_missing=0 gap_events=0 concealed=0 decoded=100 catchups=0 catchup_frames=0 q_min=2 q_avg=4.10 q_max=6`

`PIPE/AUDIOOUT win=12 out_calls=50 out_frames=100 aout_us=980000 aout_max_us=21000 rest_n=50 rest_err=0 rest_min=0 rest_max=0 out_dry=50 out_gap_max_us=2000 out_late=0 waits=3 wall_us=1000000 prio=64 affinity=0x40000 cpu=2`

**How crackling would be expected to show** (hypotheses, none established):
- Frames lost on the network: `frames_missing` above 0 with `gap_events`, or `frames_new` clearly below the stream's frame rate (about 100 a second is expected; the 9928 frames over 103 s of the first session was 3% short).
- Frames lost after the receiver: `decoded` below `frames_new + concealed`.
- The hardware starved: `out_late` above 0, or `out_gap_max_us` well over the device buffer's play time. With `waits` also high, the queue ran short, so the stream delivered less than the hardware consumed (compare `q_min` and `frames_missing`); with late gaps but `waits` low, frames were queued and the audio thread itself was delayed. Both readings are reasoned, not established. This does not depend on what `sceAudioOutGetRestSample` returns; `rest_*` and `out_dry` are raw values.
- Frames thrown away on purpose: `catchups` and `catchup_frames` above 0. That is the rule working, and it is audible as a skip; it is a fault only if it repeats without a stream hiccup before it.
- Delivery in bursts: `q_max` approaching the bound (10 frames for 480-sample frames at 48 kHz) shows arrivals building up faster than they are played; compare with `PIPE/SOCKQ` and `PIPE/RECVBUF`.

**How to judge #416 on hardware.** Expectations, none measured yet. Compare against the #413 probes-build logs, where the output fields were on `PIPE/AUDIO` and `aout_us` on `PIPE/RECVTIME`.
- The socket drains after a hiccup: `PIPE/SOCKQ` near zero, and back to near zero within about a second after a stream gap (before: 280 to 330 KB stayed for more than 80 s; 15 to 30 KB was always waiting in good gameplay).
- The receive thread no longer pays for the sound hardware: `acb_us` and `acb_max_us` on `PIPE/RECVTIME` small.
- The catch-up rule runs only when it should: `catchups` and `catchup_frames` above 0 once at a hiccup and 0 otherwise.
- Sound is not sitting late in the queue: `q_min` stays low. A `q_min` that stays high for many windows means audio is queued late without ever crossing the bound, which the rule does not fix.
- The output keeps pace: `out_late` and `out_gap_max_us` no worse than in the baseline logs.
- The cushion holds: after the first second `out_dry` and `waits` near 0 except right after a stream gap, and `q_avg` around 4 to 5 (the start level is 5 frames).
- The burst after a hiccup does not cost video: `decode_q_drops` on `PIPE/FPS` stays 0 during it.
- The recv thread stays on `USER_0` (9.8).
- Concealment works (#440), none measured yet: `q_avg` holds near the start level (5 frames) in windows where `frames_missing` is above 0, instead of sinking to about 1.5 as in log `37535415638`; `out_dry` and `waits` stay near 0 outside hiccups; `concealed` is about `frames_missing`, except on jumps above the cap of 5 frames, where it is lower by design.

**Record, first #416 hardware log (2026-10-12, `28452801651_vitarps5-testing.log`, build 0.1.1175, sound).** The socket backlog was gone, but sound was spotty, in two regimes in one session. Up to about 36 s the queue ran with no spare sound (`q_avg` 1.5 to 1.9) and the device ran empty constantly: `waits` and `out_dry` 10 to 40 per window, `rest_min=0`. From about 36 s to about 97 s the queue happened to sit about two frames fuller (`q_avg` about 3.7, `q_max` 5) and there was not one dry call (`out_dry=0`, `waits=0`), but with almost no margin (`rest_min=64` samples, about 1.3 ms, in most windows). So about 20 ms of spare sound is just enough and 30 ms gives one frame of margin; that is the origin of `AUDIO_REFILL_CUSHION_MS` = 30. Not yet measured on the build with the cushion.

**Record, second and third #416 hardware logs (2026-10-12, build 0.1.1179, log `29488516769_vitarps5-testing.log`).** The CEO reported the sound as all garbled. Every timing counter looked healthy: `out_dry=0` in 104 of the windows, `out_late=0`, `out_gap_max_us` 70 to 130 microseconds in normal windows, `rest_min` 64 to 576 and `rest_max` 704 to 832 samples, `q_avg` about 2.5, and 15 missing frame indexes in the whole session; the re-arm hold fired 32 times (section 6). The suspected cause is the reused play buffer (section 6, play-buffer rotation): the single buffer was refilled about 90 microseconds after `sceAudioOutOutput` returned while the device still had up to 704 samples to play. That is NOT confirmed on hardware; it is the leading suspicion because it fits the history (the 0.1.1175 "spotty" sound happened when calls ran back to back, and the cushion made that the normal case). Not yet measured on the build with the rotation. If the rotation build is still garbled, the next experiment is this: the other difference at the device boundary is that the old code only called `sceAudioOutOutput` when the rest sample read 0, while the new code calls it back to back; restoring that gate for one build would separate the two.

**Known, not changed.** `vita_audio_cleanup` frees the play blocks right after the join while the device may still have part of the last block outstanding; the code before #416 freed its ring the same way.

**What it cannot tell you.** No probe checks what the device actually plays: the counters here are about when data was handed over, never about its content. It never hears the output: a late call or a dropped frame is a risk of a gap, not proof of one. `out_late` counts only the calls this code makes, so a hardware underrun that the code does not notice is invisible. `q_*` samples are taken at pushes only, so they say nothing about the queue while the stream is silent. A `q_min` that stays low does not show that no sound was late, only that it was not queued late. `PIPE/AUDIOOUT` windows are not aligned with anything else. Values are "to be measured"; no hardware result is recorded here yet.

### 9.10 `PIPE/PRESENT` and `PIPE/UITHREAD`: are pictures presented in order and evenly?

**What it measures.** `PIPE/PRESENT` is the UI thread's own view of presentation, per window: how many times `vita_video_render_latest_frame` ran, how many found no new frame, how many presented a freshly decoded picture, whether the picture numbers it presented went forward, repeated or went backwards, how many pictures never reached the screen, and how evenly the buffer swaps were spaced. `PIPE/UITHREAD` is the UI thread's priority, affinity mask and CPU as the system reports them. Both are logging only (#416); they change nothing that is decoded, shown or when. Both are printed from `host_metrics_update_latency` on the UI thread (so no lock), under the same `show_latency` gate as `PIPE/DISPLAY`. The accounting itself runs always: a handful of integer operations per pass, no allocation, no log call and no clock read of its own (the swap interval reuses the read that already follows `vita2d_swap_buffers()`).

**Picture numbers.** Each of the two textures (`frame_texture`, `last_good_texture`) has the number of the picture it holds (`frame_texture_seq`, `last_good_texture_seq`, `vita/src/video.c`). The decode thread stores the number it already computes (the one published as `incoming_frame_seq`) when it finishes writing into `frame_texture`, under `mtx`; `promote_decoded_frame_to_last_good` swaps the two numbers together with the pointers, under the same lock. The number compared is that of the texture actually drawn. A number of 0 (unknown) is skipped, not counted.

**Why `back` exists, and the race that was closed (#416).** Before the claim existed, `vita_video_render_latest_frame` cleared `frame_ready_for_display` first and took `mtx` only later, inside `promote_decoded_frame_to_last_good`. If the decode thread finished another picture in between, the flag was true again but the swap left `frame_texture` pointing at the previously shown picture, and the next UI pass could present that old picture if no newer one had been decoded into it yet; the corrupt flag and the stamps the UI had read also belonged to the earlier picture. That was read from the code, never confirmed on a log. The claim (section 6) takes all of it in one critical section, so the race is closed. `back` is kept as the check: it should stay 0 in windows where `PIPE/DECHOLD` shows `rb_bad=0`, and a non-zero value there is a regression, not noise. Not measured on hardware yet. `snapshot_p95_us` on `PIPE/DISPLAY` is the time from render entry to the end of the claim, so it includes the wait for `mtx` (up to one decode if the UI loses the race).

**Reading before/after logs (reasoned, not measured).** Compared with builds before the claim: `overwrites` on `PIPE/FPS` reads higher, because a picture overwritten while the UI waited for the lock is now counted; swaps, `display_fps` and `shown` read lower by the rate of lost races, because the stale re-present is gone; and the pickup sample is dropped (not counted) when the decoder published a newer picture while the UI waited, so the `pickup_*` percentiles of `PIPE/DISPLAY` lean slightly high. None of these is a regression by itself.

**Fields.** `PIPE/PRESENT passes= misses= shown= back= same= back_max= skip_frames= gaps=a,b,c,d,e,f gap_max_us=` and `PIPE/UITHREAD prio= affinity=0x cpu= last_cpu= info_rc=`

| Field | Meaning |
|---|---|
| `passes` | Calls of `vita_video_render_latest_frame` in the window, every call, including those that return at the teardown gate. |
| `misses` | Of those, calls that returned because no frame was ready. |
| `shown` | Of those, calls that presented a freshly decoded picture: not a frozen last-good repeat. |
| `back` | Presents whose picture number is lower than the previous present's. |
| `same` | Presents whose number equals the previous present's. |
| `back_max` | Largest backwards step, in frames. |
| `skip_frames` | Sum over forward presents of (number minus previous number minus 1): pictures that never reached the screen. |
| `gaps=a,b,c,d,e,f` | Number of swap-to-swap intervals shorter than 12 ms, 12 to 21, 21 to 29, 29 to 38, 38 to 55 and 55 ms or more (`PRESENT_GAP_EDGE_*_US`, `vita/src/video.c`). The previous swap time carries across windows. |
| `gap_max_us` | Longest swap-to-swap interval. |
| `prio`, `affinity`, `cpu`, `last_cpu`, `info_rc` | `currentPriority`, `currentCpuAffinityMask` (hex), `currentCpuId`, `lastExecutedCpuId` of the UI thread from `sceKernelGetThreadInfo`, and its return code (0 is success; the other fields are 0 otherwise). Printed at the first window and again only when `prio`, `affinity` or `cpu` differs from the last print; reset with the stream. |

Example (made-up numbers): `PIPE/PRESENT passes=2400 misses=2340 shown=58 back=2 same=1 back_max=2 skip_frames=3 gaps=0,31,20,5,2,1 gap_max_us=61000`

`PIPE/UITHREAD prio=160 affinity=0x70000 cpu=1 last_cpu=1 info_rc=0`

**How to read it.** A steady 60 pictures a second would put almost all swaps in the 12 to 21 ms bucket; a 30 fps picture, in 29 to 38. A spread over several buckets, or `gaps` entries at 38 ms and above, is uneven presentation. `back` or `same` above 0 means an older picture was shown again after a newer one, which is the "frames out of order" the CEO reported and the race above would produce; `skip_frames` says how many pictures were decoded but never shown. `passes` minus `misses` is the number of pictures picked up; `shown` below that means some were frozen. `PIPE/UITHREAD` shows whether the UI thread sits on a core and priority that could compete with the media threads (all on 64, one per core, 9.8).

**What it cannot tell you.** `shown` and the gap histogram count buffer swaps, not what the panel displayed: a swap does not say which refresh showed it. Picture numbers are the decoder's echoed number, so they are only as good as that echo (0 is skipped). When the decoder's read-back number is rejected, the texture's number falls back to the number that was fed in; since the decoder holds 4 to 5 pictures, that gives a false forward jump followed by a false `back`, so trust `back` only in windows where `PIPE/DECHOLD` shows `rb_bad=0`. After a real backwards step the next forward step over-counts `skip_frames`, and the stale re-present is counted in `shown`. With `show_latency` off nothing is printed and the window is not reset. Values are "to be measured"; no hardware result is recorded here yet.
